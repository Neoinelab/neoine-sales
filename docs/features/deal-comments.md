## 1. 개요

- 목적: Action에 딸린 글 칸이던 Memo를 **Comment**라는 별도 엔티티로 분리한다. **Comment는 항상 Deal 하나에 연결되고, 추가로 그 Deal의 특정 Action 하나에 연결될 수도 있다(CM-R2).** 한 Deal·Action에 여러 Comment를 남길 수 있고, 작성자·작성 시각이 Comment마다 남는다.
- 사용자(역할): 조회는 로그인한 모든 역할(admin·sales·user)이다. 작성은 sales·admin이 하며 어느 Deal·어느 Action에든 쓸 수 있다. 삭제는 작성자 본인 sales와 admin이 한다. 수정 기능은 없다(CM-R10, 2026-11-17 폐지). 읽음 처리는 그 Deal의 Owner만 한다(CM-R28).
- 범위
  - API: `POST /deals/{code}/comments`, `GET /deals/{code}/comments`, `GET /deal-comments/{comment_id}`, `DELETE /deal-comments/{comment_id}`, `POST /deals/{code}/comment-reads`(Owner 읽음 처리), `GET /deals/{code}/comment-counts`(읽지 않은 수)
  - Action 등록 요청의 `comment`(새 Action에 Action Comment를 함께 남김), Next Action 종료 요청의 `comment`(종료한 Action에 Action Comment를 남김) — 예전 `memo`를 대신한다
  - Action 삭제·Deal 삭제 때 Comment 처리, Deal 삭제 영향의 `comment_count`
  - Comment가 Deal History에 남기는 항목(새 구분 `comment`)
  - Action 검색 키워드가 Action Comment 본문도 찾는 것
  - 기존 `deal_actions.memo` 값을 Comment로 옮기고 컬럼을 없애는 마이그레이션
  - (2026-11-17 추가) Owner 읽음 상태 `deal_comments.read_at`(CM-R26~R31), 연결 Action 요약 응답(CM-R9), 화면: Comments 탭·Actions 표 Comment 열·Action 상세 팝업 Comment 영역(CM-R32~R46)
  - (2026-11-18 추가) Deal 응답(목록 행·상세)의 읽지 않은 Comment 수 `unread_comment_count`(CM-R47), Deals 목록 Deal 이름 옆 배지(CM-R48)
- 범위 밖(다른 feature 또는 후속)
  - Comment 수정(2026-11-17 폐지), 알림(메일·푸시)·멘션·첨부(요청 없음), 읽지 않은 수로 Deals 목록을 거르거나 정렬하기(요청 없음)
  - Deals 목록 표의 나머지 칸·열 순서 → DL(DL-R28), Deal 상세·등록·수정 응답의 나머지 필드 → DD(DD-R2)·DE
  - Action 등록·수정·삭제의 나머지 규칙 → AC, Next Action 상태 변경의 나머지 규칙 → NA, Reports `deal.comment`·`action.comment` 필드 → RQ(RQ-R60·R61), 리비전 그래프·스키마 공통 규칙 → SC(SC-R24·R25), History 목록·자르기 → DD(DD-R17·R20), 사용자 연결 → US(US-R17)
  - Comment 첨부·멘션·알림 — 요청 없음
- 관련 화면·메뉴: Deals → Deal 상세의 "Comments" 탭(맨 오른쪽), Actions 탭(Comment 열·Action 상세 팝업), Deal History 탭(구분 Comment), Deal 삭제 확인.

## 2. 명세 (SDD)

### 2.1 용어

| 용어 | 뜻 |
| --- | --- |
| Comment | Deal에 연결된 메시지 한 건(CM-R2). 주로 다른 사람이 Deal Owner에게 전하는 글이다. 본문, 작성자, 작성 시각, 소속 Deal, 선택적인 연결 Action, Owner 읽음 시각을 가진다. 작성한 뒤에는 고칠 수 없다(CM-R10). 화면·문구 표기는 영문 "Comment"다 |
| Deal Comment | 연결 Action이 없는 Comment(`action_id` null). Deal 자체에 대한 글 |
| Action Comment | 소속 Deal의 Action 하나에 연결된 Comment(`action_id` = 그 Action id) |
| Deal 소속 Comment | 한 Deal에 연결된 Comment 전부(Deal Comment + Action Comment). 목록(CM-R7)·삭제 영향(CM-R18)·Reports `deal.comment`(RQ-R61)의 범위 |
| 작성자(`author`) | Comment를 쓴 사용자. 바뀌지 않으며 수정·삭제 권한의 기준이다 |
| 종료 Comment | Next Action을 종료로 바꾸며 함께 보낸 글. 그 Action의 Action Comment가 된다(CM-R15) |
| 예전 Memo | 2026-11-17 리비전 전 Action의 `memo` 칸. 리비전이 Action Comment로 옮긴 뒤 컬럼을 없앤다(CM-R21~R23) |
| 읽음 / 읽지 않음 | Comment의 속성. Deal Owner가 읽었으면 읽음(`read_at` 값 있음), 아니면 읽지 않음(`read_at` null). 보는 사람과 무관하게 모두에게 같다(CM-R26) |
| 읽음 처리 | Deal Owner가 Comments 탭이나 Action 상세 팝업에서 Comment를 보았을 때 `read_at`을 채우는 것(CM-R28, CM-R38) |
| 연결 Action 요약 | Action Comment 응답에 붙는 그 Action의 id·수행일·진행사항·Next Action(CM-R9) |
| 읽지 않은 수 | Deal 단위(그 Deal의 읽지 않은 Comment 수)와 Action 단위(그 Action의 읽지 않은 Comment 수)가 있다(CM-R29) |

### 2.3 비즈니스 규칙

관계(서두 규칙)
- **CM-R2** Comment는 **항상 Deal 하나에 연결된다**(`deal_id` 필수). 추가로 **그 Deal의 Action 하나에 연결될 수도 있다**(`action_id` 선택). 연결 Action은 반드시 같은 Deal 소속이다(DB 복합 FK와 CM-R5). 소속 Deal과 연결 Action은 작성할 때 정하고 바꿀 수 없다: `action_id`가 없거나 null이면 Deal Comment, 값이 있으면 그 Action의 Action Comment다. Comment는 작성 뒤 바뀌지 않는다(본문 수정 없음, CM-R10). 바뀔 수 있는 값은 읽음 시각(CM-R26)뿐이다. 한 Deal의 Comment(Deal 소속 Comment)는 Deal Comment와 그 Deal의 모든 Action Comment를 합친 것이다.

본문
- **CM-R1** 본문 규칙(작성·Action 등록 `comment`·종료 Comment 공통, 위에서부터 첫 위반만):
  1. NUL 문자가 있으면 422 `invalid-value` "Comment에는 NUL 문자를 쓸 수 없습니다"(PL-R16)
  2. (필수인 곳만 — 작성) 앞뒤 공백을 지운 값이 비면 422 `invalid-value` "Comment를 입력하세요."

  통과하면 앞뒤 공백을 지운 값을 저장한다. 안쪽 줄바꿈·공백은 그대로다. 길이 상한이 없어 자르지 않는다(예: 20,000자). 선택인 곳(Action 등록 `comment`, 종료 Comment)은 비었거나 공백뿐이면 Comment를 만들지 않는다.

작성 API
- **CM-R3** `POST /deals/{code}/comments`는 업무 쓰기다(sales·admin, user는 PL-R6 403). 본문 `{"body": <문자열>, "action_id": <정수|null>}` — `body` 필수(누락·null·문자열 아님은 422 `request-validation`), `action_id` 선택(JSON 정수 1~2^53−1 또는 null, 형식 위반 422 `request-validation`, PL-R15와 같은 범위). 모르는 키(`author`·`author_user_id`·`deal_code`·`memo` 등)는 422 `request-validation`. 성공은 201, 헤더 `Location: /api/v1/deal-comments/<id>`, 본문 `DealCommentResponse`(CM-R9).
- **CM-R4** 서버가 정하는 값: 작성자 = 요청자, `created_at` = `updated_at` = 요청 시각, 소속 Deal = 경로의 Deal. Deal Owner 여부와 Action 작성자 여부는 보지 않는다(남의 Action에도 쓴다). 작성자가 그 순간의 Deal Owner이면 `read_at` = 요청 시각이다. 그 밖의 사람(admin 포함)이 쓰면 null이다(CM-R26).
- **CM-R5** `action_id`가 있으면 그 id의 Action이 있고 경로의 Deal 소속이어야 한다. 없는 id, 다른 Deal의 Action이면 422 `invalid-value` "선택한 Action이 이 Deal에 없습니다."다(경로 자원은 Deal이므로 404가 아님).
- **CM-R6** 작성 판정 순서: 401 → CSRF 403(PL-R9) → user 403(PL-R6) → 요청 형식 422 `request-validation` → 없는 Deal·형식이 틀린 code 404 `not-found` "Deal을 찾을 수 없습니다."(DD-R1) → 본문 422(CM-R1) → 연결 Action 422(CM-R5). 거절되면 Comment·History가 그대로다. 성공하면 Comment와 History 항목(CM-R13)이 한 트랜잭션으로 저장된다.

조회 API
- **CM-R7** `GET /deals/{code}/comments`는 로그인한 모든 역할이 부른다. 없는 Deal·형식이 틀린 code는 404 "Deal을 찾을 수 없습니다.". 쿼리 `action_id`(선택, 정수, 형식은 PL-R15): 없으면 그 Deal 소속 Comment 전부(Deal Comment와 Action Comment 모두), 있으면 그 Action의 Action Comment만이다. 그 Deal에 없는 Action id는 오류 없이 0건이다. 응답은 `{"items": DealCommentResponse[]}`(키 `items`뿐), 페이지 없음, 다른 Deal의 Comment는 섞이지 않는다. 순서는 `created_at` 내림차순이고, 같으면 `id` 내림차순이다(최근 것이 먼저, 2026-11-17 변경). Reports의 이어 붙이기 순서(RQ-R60·R61, 오래된 순)는 바뀌지 않는다.
- **CM-R8** `GET /deal-comments/{comment_id}`는 로그인한 모든 역할이 부른다. 없는 id는 상한값이어도 404 `not-found` "Comment를 찾을 수 없습니다."(형식은 PL-R15).
- **CM-R9** `\`DealCommentResponse\` 키는 정확히 다음 9개다: \`id\`(정수), \`deal_code\`(항상 값 있음), \`action_id\`(정수 또는 null, 키는 항상 있음), \`action\`(연결 Action 요약 \`{id, acted_on, action, next_action}\` 또는 null, 키는 항상 있음, 2026-11-17), \`body\`, \`author\`(UserRef, 퇴사자도 \`resigned\` true·\`label\` "<이름>(퇴사)"), \`created_at\`, \`updated_at\`, \`read_at\`(시각 또는 null, 키는 항상 있음, 2026-11-17). \`action\`의 값은 응답 시점 그 Action의 현재 수행일(\`YYYY-MM-DD\`)·진행사항·Next Action이다(null 가능). Deal Comment는 \`action\`이 null이다.` 시각 표기는 TM-R8.

수정 API
- **CM-R10** (폐지 2026-11-17) Comment 수정. Comment는 메신저 메시지처럼 고칠 수 없다. `PUT /deal-comments/{comment_id}` 경로는 없다. 같은 경로에 GET·DELETE가 있으므로 PUT 요청은 405 Method Not Allowed다. 잘못 쓴 Comment는 지우고 다시 쓴다(CM-R11).

삭제 API
- **CM-R11** `DELETE /deal-comments/{comment_id}`는 업무 쓰기다. 성공은 204(본문 없음)이고 행을 물리 삭제하며 History 1건(CM-R13)을 남긴다. 판정 순서: 401 → CSRF 403 → user 403(없는 id여도 먼저) → id 형식 422(PL-R15) → 없는 Comment·이미 지운 Comment 404 → 작성자가 아님 403 `forbidden` "본인 Comment 또는 admin만 삭제할 수 있습니다.". 거절되면 Comment·History가 그대로다.

권한
- **CM-R12** 작성은 sales·admin 누구나 모든 Deal·모든 Action에 한다. 삭제는 `can_delete_comment`를 따른다. admin은 모든 Comment를, sales는 자기가 작성자인 Comment만 지운다. user는 자기 것이어도 지우지 못한다(Action의 AC-R17과 같은 규칙). admin이 남의 Comment를 지우면 History 변경자는 admin이다. Action 작성자나 Deal Owner라는 이유로 남이 쓴 Comment를 지울 수는 없다. 읽음 처리 권한은 CM-R28이 정한다.

Deal History
- **CM-R13** Comment 작성·삭제는 소속 Deal의 History에 1건씩 남긴다. 구분 `comment`(새 값), 변경자 = 요청자, 시각 = 요청 시각, 자르기 DD-R20.
  - 대상: Deal Comment는 `"Comment"`, Action Comment는 `"Action Comment (<수행일 YYYY-MM-DD> <유형 이름>)"`(기록 시점의 그 Action 수행일·유형 이름. 나중에 Action이 바뀌어도 이미 남은 문구는 그대로).

  | 행동 | 변경 전 | 변경 후 |
  | --- | --- | --- |
  | 작성 | "" | "등록: <본문>" |
  | 삭제(CM-R11) | "<본문>" | "삭제" |

  Action·Deal 삭제로 함께 지워지는 Comment는 Comment마다 항목을 남기지 않는다(CM-R16, CM-R18). Comment 작성·삭제는 Deal 값, Deal `updated_at`·`last_updated_on`, Action 값·`updated_at`을 바꾸지 않는다. 읽음 처리는 History에 남지 않는다(CM-R28). 2026-11-17 이전에 남은 "수정: …" 이력 행은 그대로 둔다.

Action과의 연동
- **CM-R14** Action 등록 요청(AC-R2)의 선택 필드 `comment`(문자열, 생략하면 ""): CM-R1(선택)을 통과해 비지 않으면 새 Action의 Action Comment 1건을 같은 트랜잭션에서 만든다(작성자 = 요청자, `created_at` = `updated_at` = 요청 시각 — 수행일과 무관). 판정 위치는 내용 422(AC-R3) 바로 다음, 수행일 422(AC-R35) 앞이다. History는 Action 등록 줄 다음에 Comment 등록 줄(CM-R13, 대상 "Action Comment (<새 Action 수행일> <유형>)")이 같은 시각으로 남는다(그래서 History 맨 위는 Comment 등록 줄). 등록이 어떤 이유로든 거절되면 Comment도 남지 않는다. 예전 `memo` 키는 422 `request-validation`이다. 등록자가 그 순간의 Deal Owner이면 그 Comment는 읽음으로 생긴다(CM-R26).
- **CM-R15** 종료 Comment: Next Action 상태 변경 본문(NA-R2)의 `memo`가 `comment`(문자열, 생략하면 "")로 바뀐다. 종료 상태로 바꾸며 `comment`가 비지 않으면 그 Action의 Action Comment 1건을 같은 트랜잭션에서 만든다(작성자 = 요청자 — admin이 남의 Action을 닫으면 admin, 시각 = 요청 시각). Action 내용은 바뀌지 않는다. History는 Next Action 줄(NA-R8, 변경 후는 라벨만) 다음에 Comment 등록 줄이 같은 시각으로 남는다. Open으로 되돌리며 비지 않은 `comment`를 보내면 422 `invalid-value` "Open으로 되돌릴 때는 Comment를 남길 수 없습니다."(공백뿐이면 허용). 검사 순서: Comment NUL → Open+Comment → Next Action 없음 409 → 같은 상태 409(NA-R7). 거절되면 Comment가 생기지 않는다. 예전 `memo` 키는 422 `request-validation`이다. Action 등록 때 이전 Next Action 종료(AC-R7 ④)는 Comment를 만들지 않는다. 상태를 바꾸는 사람이 Deal Owner이면 읽음으로 생긴다. admin이나 Owner가 아닌 Action 작성자가 닫으면 읽지 않음으로 생긴다.
- **CM-R16** Action 삭제(AC-R16): 그 Action의 Action Comment가 DB CASCADE로 같은 트랜잭션에서 함께 지워진다. Deal Comment와 다른 Action의 Comment는 그대로다. Action 삭제 History 줄의 변경 후는 함께 지운 Comment가 없으면 "삭제", 1건 이상이면 "삭제 (Comment <N>건 함께 삭제)"다.
- **CM-R17** Action 수정(AC-R13)은 Comment를 바꾸지 않는다. 수정 요청의 `memo`·`comment` 키는 422 `request-validation`이다. Action 응답(AC-R20)에는 `memo`도 Comment 필드도 없다(Comment는 CM-R7로 읽고, 읽지 않은 수는 CM-R29로 읽는다).
- **CM-R18** Deal 삭제(DD-R25): 그 Deal 소속 Comment 전부가 함께 지워진다. `GET /deals/{code}/deletion-impact` 응답에 `comment_count`(그 Deal 소속 Comment 수, 다른 Deal 제외)가 추가된다(DD-R22).
- **CM-R19** Action 검색 `keyword`(NA-R14): 진행사항·Next Action 중 하나 또는 **그 Action의 Action Comment 본문 중 하나**가 대소문자 구분 없이 부분 일치하면 맞다(`%`·`_`·`\`는 글자 그대로). Deal Comment는 Action 검색에 영향이 없다.

사용자
- **CM-R20** `deal_comments.author_user_id`는 users FK RESTRICT라 Comment를 쓴 사용자는 사용자 연결(US-R17, 17종)이 있어 물리 삭제 대신 퇴사 처리된다. 퇴사한 작성자의 Comment는 남고 응답 `author.resigned`가 true다.

Reports
- **CM-R25** Reports 카탈로그에 Comment 필드 두 개가 생긴다(규칙 소유 RQ): `deal.comment`(Deal 필드 — 그 Deal 소속 Comment 전부, Action 연결 여부 무관, RQ-R61)와 `action.comment`(Action 필드 — 그 Action의 Action Comment만, RQ-R60). 따라서 Action Comment 본문은 두 필드에 모두 나타나고 Deal Comment 본문은 `deal.comment`에만 나타난다.

Owner 읽음 상태(2026-11-17 추가)
- **CM-R26** 읽음은 Comment의 속성이다. `read_at`이 null이면 읽지 않음, 값이 있으면 읽음이다. 누가 조회해도 같은 값이 보인다. 생성할 때(작성 API, Action 등록 `comment`, 종료 Comment) 작성자가 **그 순간의 Deal Owner**이면 `read_at` = 작성 시각이다. 그 밖의 사람이 쓰면 null이다. admin도 Owner가 아니면 null이다. Owner는 재직 sales만 될 수 있다(DE).
- **CM-R27** Deal Owner가 바뀌어도(DE·DD 변경) 기존 Comment의 `read_at`은 그대로다. 이전 Owner가 읽은 Comment는 계속 읽음이고, 읽지 않은 Comment는 새 Owner가 읽음 처리할 수 있다. Owner 변경 뒤에는 새 Owner가 쓴 Comment만 자동 읽음이다.
- **CM-R28** `POST /deals/{code}/comment-reads`는 그 Deal의 **현재 Owner만** 부른다. 업무 쓰기이므로 PL-R6과 CSRF(PL-R9)를 적용한다.
  - 본문은 `{"comment_ids": [<정수>, …]}`이다. 값은 1~500개이고, 각 값은 PL-R15 범위의 JSON 정수다. 중복은 한 번으로 본다. 누락, 빈 배열, 501개 이상, 정수가 아닌 값, 범위 밖 값, 모르는 키는 422 `request-validation`이다.
  - 판정 순서: 401 → CSRF 403 → user 403(PL-R6) → 요청 형식 422 → 없는 Deal·형식이 틀린 code 404 "Deal을 찾을 수 없습니다." → Owner가 아님 403 `forbidden` "Deal Owner만 Comment를 읽음 처리할 수 있습니다."(admin 포함) → 처리.
  - 처리: 경로 Deal 소속이고 `read_at`이 null인 Comment의 `read_at`을 요청 시각으로 채운다. 다른 Deal의 id, 없는(지워진) id, 이미 읽은 id는 오류 없이 건너뛴다. 이미 읽은 Comment의 `read_at`은 바뀌지 않는다(멱등).
  - 성공은 204(본문 없음)다. History, Deal·Action 값과 `updated_at`·`last_updated_on`, Comment의 본문과 `updated_at`은 바뀌지 않는다.
- **CM-R29** `GET /deals/{code}/comment-counts`는 로그인한 모든 역할이 부른다. 응답은 `{"unread": <정수>, "by_action": [{"action_id": <정수>, "unread": <정수>}, …]}`이다.
  - `unread`는 그 Deal 소속 Comment(Deal Comment와 Action Comment) 중 `read_at`이 null인 수다.
  - `by_action`에는 읽지 않은 Comment가 1건 이상인 Action만 `action_id` 오름차순으로 넣는다. 다른 Deal의 Comment는 섞이지 않는다.
  - 없는 Deal·형식이 틀린 code는 404 "Deal을 찾을 수 없습니다."다.
  - 결정 근거(2026-11-17): Action 응답에 필드를 넣는 대신 집계 경로 하나로 준다. 그러면 AC 응답 계약과 Action 응답을 만드는 유스케이스 5곳을 바꾸지 않는다. Deal 상세 화면은 계속 이 경로를 쓴다(CM-R39). (2026-11-18) Deals 목록용으로 Deal 응답에 같은 값 `unread_comment_count`(CM-R47)를 추가했다.
- **CM-R30** 읽음 시각은 Comment 행에 있으므로 Comment·Action·Deal을 지우면 함께 사라진다. 사용자 연결(US-R17)은 바뀌지 않는다(새 사용자 FK 없음).
- **CM-R31** 마이그레이션은 새 리비전으로 한다(down_revision `d2f6b8a4c931`, expand). 순서는 다음과 같다.
  - ① `deal_comments.read_at TIMESTAMPTZ NULL`을 추가한다.
  - ② 기존 모든 행을 `read_at = created_at`으로 채운다. 이 단계는 새 컬럼에 값을 넣는 것뿐이다. 기존 값을 덮어쓰거나 행을 지우지 않는다.
  - ③ CHECK `ck_deal_comments_read_after_created`와 부분 인덱스 `ix_deal_comments_deal_id_unread`를 만든다.
  - upgrade에는 `DELETE`·`TRUNCATE`·컬럼 drop이 없다. 구 앱은 새 컬럼을 무시하므로 코드만 롤백해도 동작한다. 그 뒤 생긴 Comment는 null(읽지 않음)로 남는다.
  - downgrade는 인덱스·CHECK·`read_at`을 drop한다. 읽음 시각만 사라지고 다른 데이터는 그대로다. WARNING 로그에 읽음 행 수를 남긴다.
  - product 적용은 사람 승인과 `pg_dump` 뒤에만 한다.

Deal 응답의 읽지 않은 수(2026-11-18 추가)
- **CM-R47** Deal을 돌려주는 응답에 `unread_comment_count`가 있다. 대상은 `GET /deals` 행 `DealRowResponse`(DL-R14)와 `DealDetailResponse`(DD-R2, 상세·등록·수정·변경 적용 응답 포함)다.
  - 형식: JSON 정수, 0 이상, 키는 항상 있고 null이 아니다.
  - 값: 그 Deal 소속 Comment(Deal Comment와 Action Comment) 중 `read_at`이 null인 수다. 같은 순간 `GET /deals/{code}/comment-counts`의 `unread`(CM-R29)와 같다. 다른 Deal의 Comment는 섞이지 않는다.
  - 응답할 때마다 계산하고 저장하지 않는다. 그래서 Comment 작성·삭제·읽음 처리, Action·Deal 삭제가 다음 조회에 바로 반영된다. Deal 값과 `updated_at`·`last_updated_on`은 이 값 때문에 바뀌지 않는다.
  - 보는 사람과 무관하게 같다(CM-R26). 모든 역할이 같은 값을 받는다.
  - 목록 조건·정렬·`total`·페이지에 영향이 없다. 이 값으로 거르거나 정렬하는 파라미터는 없다. `unread_comment_count` 쿼리나 `sort=unread_comment_count`를 보내면 DL-R3·DL-R13대로 422 `request-validation`이다.
  - 목록은 한 질의 안에서 센다(2.2). 행마다 집계 경로를 부르지 않는다.

마이그레이션(기존 Memo 이전과 컬럼 제거)
- **CM-R21** 리비전(SC-R24)은 한 트랜잭션에서 ① `uq_deal_actions_id` 추가 → ② `deal_comments` 생성 → ③ 기존 Memo 복사(CM-R22) → ④ 건수 점검 → ⑤ `deal_actions.memo` drop(CM-R23) 순으로 적용한다. upgrade에 `DELETE`·`UPDATE`·`TRUNCATE`가 없다.
- **CM-R22** 복사: `btrim(memo) <> ''`인 `deal_actions` 행마다 Action Comment 1건을 넣는다 — `deal_id` = 그 행 `deal_id`, `action_id` = 그 행 `id`, 작성자 = 그 행 `actor_user_id`, 본문 = `memo` 값 그대로(종료 메모를 줄바꿈으로 덧붙인 여러 줄도 나누지 않음), `created_at` = 그 행 `created_at`, `updated_at` = 그 행 `updated_at`. 빈 값·공백뿐인 Memo는 옮기지 않는다(앱은 늘 trim해 저장하므로 공백뿐인 값은 원래 없다). History 항목은 만들지 않는다. 점검: 넣은 행 수가 `btrim(memo) <> ''` 행 수와 다르면 `RuntimeError` "Memo를 Comment로 옮긴 건수(<넣은 수>)가 Memo가 있는 Action 수(<대상 수>)와 다릅니다."로 중단한다(롤백되어 컬럼 drop을 포함해 아무것도 바뀌지 않음).
- **CM-R23** 컬럼 제거: 점검을 통과한 뒤에만 `deal_actions.memo`를 drop한다. 비지 않은 값은 모두 Comment로 옮겨진 뒤라 정보가 남는다(빈 값만 버림). 이 drop은 2026-11-05 데이터 삭제 금지 규칙(SC-R8)에 대한 **사용자 승인 contract**(2026-11-17, "memo 데이터가 실제로 없으므로 바로 제거")다. 하위 호환(SC-R9 예외, 사용자 승인): 구 앱은 `memo` 컬럼을 읽고 쓰므로 코드만 롤백하면 Action 조회·등록·수정·Reports가 실패한다(데이터 손상 없음). 롤백할 때는 `downgrade -1`을 함께 실행하거나 배포 전 `pg_dump`로 복원한다. product 적용은 사람 승인과 배포 전 `pg_dump` 뒤에만 한다.
- **CM-R24** downgrade(정보 일부 복원): `deal_actions.memo TEXT NOT NULL DEFAULT ''`를 추가 → 각 Action의 `memo`를 그 Action의 Action Comment 본문을 `created_at`·`id` 오름차순으로 줄바꿈("\n")으로 이은 값으로 채움(Action Comment가 없으면 '') → 서버 기본값 제거 → `deal_comments` drop → `uq_deal_actions_id` drop. 옮겼던 Memo(Action당 Comment 1건)는 원래 값 그대로 돌아온다. 되돌릴 수 없어 **소실되는 것**: Deal Comment 전부, Action Comment의 작성자·작성 시각(여러 건이면 한 Memo로 합쳐짐), 다른 사람이 쓴 Action Comment의 구분. downgrade 문서·로그에 이 소실을 알린다(WARNING 로그에 소실되는 Deal Comment 건수).

### 2.4 상태와 전이

Comment의 상태는 읽음 여부(`read_at`)뿐이다. 본문·소속 Deal·연결 Action은 작성 뒤 바뀌지 않는다(CM-R2, CM-R10).

| 사건 | Comment 결과 |
| --- | --- |
| 작성 | 생김 |
| Owner가 작성 | 읽음으로 생김 |
| Owner가 읽음 처리 | 읽지 않음 → 읽음(되돌아가지 않음) |
| 삭제 | 없어짐 |
| 연결 Action 삭제 | 그 Action Comment 없어짐(CM-R16) |
| 소속 Deal 삭제 | 그 Deal 소속 Comment 모두 없어짐(CM-R18) |
| 작성자 퇴사 | 남음, `author.resigned` true |
- 표에 `| Deal Owner 변경 | 읽음 상태 그대로(CM-R27) |` 행을 추가한다.

바뀌는 기존 계약(소유 문서는 교체 문구 파일 참고)
- `DealActionCreateRequest`: `memo` 삭제, `comment: string = ""` 추가(CM-R14). `DealActionUpdateRequest`: `memo` 삭제(CM-R17). `NextActionStatusRequest`: `memo` → `comment`(CM-R15). `DealActionResponse`: `memo` 삭제. — **API 호환 깨짐**(사용자 승인 2026-11-17, 별칭 없음, 클라이언트는 이 저장소 프런트뿐)
- `GET /deals/{code}/history`: `category` enum에 `comment` 추가(하위 호환 추가). `DealDeletionImpactResponse`에 `comment_count` 추가(하위 호환 추가).
- Reports 카탈로그: `action.memo` → `action.comment`(RQ-R60, **호환 깨짐**), `deal.comment` 추가(RQ-R61, 하위 호환 추가).
- OpenAPI: Comment 경로 5개·작업 6개(`DELETE·GET /api/v1/deal-comments/{comment_id}`, `GET /api/v1/deals/{code}/comment-counts`, `POST /api/v1/deals/{code}/comment-reads`, `GET·POST /api/v1/deals/{code}/comments`; 수정 `PUT` 없음)(라우터 태그 `deal-comments`, 쓰기는 403·404·422, 조회는 404·422 문서화), `DealCommentResponse`의 `action_id`는 required + nullable, `deal_code`는 required + non-null, `body`에 `maxLength`가 없다.
- (2026-11-17) `PUT /deal-comments/{id}`·`DealCommentUpdateRequest` 삭제(**API 호환 깨짐**, 사용자 결정, 클라이언트는 이 저장소 프런트뿐). `DealCommentResponse`에 `action`(nullable 객체 `DealCommentActionSummary` `{id, acted_on, action, next_action}`)과 `read_at`(nullable) 추가(하위 호환 추가). 목록 순서 최근순(CM-R7, 동작 변경). 새 경로는 `comment-counts`·`comment-reads` 2개(태그 `deal-comments`).
- (2026-11-18) `DealRowResponse`·`DealDetailResponse`에 required 정수 `unread_comment_count`(minimum 0) 추가(CM-R47, 하위 호환 추가). `GET /deals` 쿼리 파라미터는 그대로다. 마이그레이션 없음.

### 2.7 화면 동작

화면은 Deal 상세(`/deals/:dealCode`) 기준이다. 탭 틀은 DD-R27, Actions 표·팝업의 나머지는 AC, 종료 대화상자는 NA가 소유한다. 아래는 Comment 부분만 정한다. "Owner"는 화면이 가진 Deal의 현재 Owner(`deal.ownerId`)를 말한다.

- **CM-R32** Comments 탭: 상세 탭 목록의 **맨 오른쪽(네 번째)** 탭 "Comments"이고 주소는 `?tab=comments`다(DD-R27). 모든 역할이 연다. 탭 이름 옆에 Deal 단위 읽지 않은 수 배지가 붙는다(CM-R39). 탭 패널은 위에서부터 Comment 목록(CM-R33), 입력 칸(CM-R35) 순이다.
- **CM-R33** Comment 목록(탭·팝업 공통, 목록 이름 "Comment 목록"): 서버 순서(최근 것이 위, CM-R7)를 그대로 보인다.
  - 항목 첫 줄: 작성자(사용자 표기, 퇴사자 "<이름>(퇴사)")와 작성 시각 `YYYY-MM-DD HH:mm`(TM 표기).
  - 읽지 않은(`read_at` null) 항목에는 모든 사람에게 배지 "읽지 않음"이 붙는다.
  - Owner가 연 화면에서는 읽음 처리 때문에 배지가 곧 사라진다. 그래서 열 때 읽지 않음이던 항목은 그 화면이 열려 있는 동안 배지 "NEW"를 대신 보인다.
  - 그 아래 본문을 보인다(줄바꿈 그대로, 자르지 않음).
  - 처음 읽는 동안은 "불러오는 중…", 0건이면 "등록된 Comment가 없습니다.", 읽기 오류는 오류 배너(PL-R37, 서버 문구)다.
  - "수정" 버튼은 없다(CM-R10).
- **CM-R34** 연결 Action 표시(Comments 탭만):
  - `action`이 있는 항목은 본문 위 상자(이름 "연결된 Action")에 응답의 `action.acted_on`·`action.action`(진행사항)·`action.next_action`을 "수행일 · 진행사항 · Next Action" 순으로 보인다. 빈 값은 "—"다.
  - 상자 안에 버튼 "Action 보기"가 있고, 누르면 CM-R37로 그 Action 상세 팝업으로 간다.
  - `action`이 null인 항목은 상자 대신 작은 표시 "Deal Comment"를 보인다.
  - 탭의 입력 칸에는 Action 선택이 없다.
- **CM-R35** 입력 칸(탭·팝업 공통, `canWrite`(sales·admin)에게만): 목록 **아래**에 기본으로 펼쳐진 여러 줄 칸 하나(접근 이름 "Comment 입력", placeholder "Comment를 입력하세요")와 버튼 "저장"이 있다.
  - 칸 안에서 Enter(Shift 없이, 한글 조합 중이 아님)를 누르면 저장한다. Shift+Enter는 줄을 바꾼다. "저장" 버튼도 같은 저장이다.
  - 화면 검증: 앞뒤 공백을 지운 값이 비면 칸 아래 "Comment를 입력하세요."를 보이고 요청하지 않는다(다시 치면 문구를 지운다). 보내는 본문은 입력 그대로다(정규화는 서버 CM-R1).
  - Comments 탭은 Deal Comment(`action_id` 없음)를 만든다. Action 상세 팝업은 그 Action의 Action Comment(`action_id` = 그 Action id)를 만든다. Action 작성자나 Owner가 아니어도 된다.
  - 저장 중에는 칸과 버튼이 꺼진다.
  - 성공하면 칸을 비우고 포커스를 칸에 둔다. 새 Comment는 목록 **맨 위**에 보인다(최근순). 별도 알림은 없다.
  - 실패하면 칸 아래 오류 배너(서버 문구)를 보이고 입력을 유지한다. user에게는 입력 칸과 "저장"이 없다.
- **CM-R36** 삭제(탭·팝업 공통):
  - `can_delete_comment`(admin은 모든 Comment, sales는 본인 Comment)인 항목에만 버튼 "삭제"(접근 이름 "Comment 삭제")가 있다.
  - 누르면 확인 대화상자가 열린다: 제목 "Comment 삭제", 문구 "이 Comment를 삭제합니다. 삭제는 Deal History에 기록됩니다.", 버튼 "취소"와 위험 "삭제"(겹친 대화상자 UI-R27·R28).
  - 성공하면 목록에서 사라지고 배지가 줄어든다. 실패하면 대화상자를 닫고 목록 위에 오류 배너(서버 문구)를 보인다.
  - "취소"·Esc는 대화상자만 닫는다.
- **CM-R37** Action으로 이동:
  - "Action 보기"를 누르면 주소를 `?tab=actions&action=<action id>`로 바꾼다(Actions 탭으로 전환).
  - Actions 탭은 `action` 파라미터가 있으면 조건 없는 기본 목록(AC-R18)에서 그 id의 Action을 찾아 상세 팝업(AC-R49)을 연다. 검색 조건과 무관하다.
  - 팝업을 열면 주소에서 `action`을 지운다(replace). 그래서 뒤로 가기·새로 고침으로 다시 열리지 않는다.
  - 목록에 그 id가 없으면 `action`을 지우고 탭 위에 오류 배너 "Action을 찾을 수 없습니다."를 보인다.
  - 다른 탭에서 주소로 바로 들어와도 같게 동작한다.
- **CM-R38** 읽음 처리(화면): **Deal Owner 본인일 때만** 한다. 다른 sales·admin·user가 열면 요청하지 않고 표시도 그대로다.
  - ① Owner의 Comments 탭에 목록이 표시되면, 그 목록의 `read_at` null 항목 id를 모아 `POST /deals/{code}/comment-reads`를 보낸다(500개씩 나눔, 없으면 보내지 않음).
  - ② Owner의 Action 상세 팝업에 그 Action의 Comment 목록이 표시되면, 그 목록의 읽지 않은 항목으로 같은 요청을 보낸다. 다른 Action의 Comment는 그대로다.
  - ③ 같은 열람 동안 같은 id는 두 번 보내지 않는다.
  - 성공하면 Comment 목록과 읽지 않은 수(CM-R29)를 다시 읽는다.
  - 실패하면 화면에 오류를 보이지 않는다. 배지가 그대로 남고, 다음 열람에서 다시 보낸다.
  - 배지만 보거나 목록 밖에 있는 Comment는 읽음이 되지 않는다.
- **CM-R39** 읽지 않은 수 배지(모든 사람에게 같다):
  - Comments 탭 배지는 `GET /deals/{code}/comment-counts`의 `unread`다. Actions 표 Comment 열 배지는 그 Action의 `by_action` 값이고, 없으면 0이다.
  - 1 이상일 때만 숫자를 보이고, 100 이상은 "99+"다. 0이면 배지가 없다.
  - 숫자는 접근 이름에 들어간다(탭 "Comments 읽지 않은 Comment 3건", 아이콘은 CM-R40).
  - Deal 상세를 열면 탭과 무관하게 집계를 한 번 읽는다. Actions 탭 이름에는 배지가 없다. Deals 목록 배지는 CM-R48이다(2026-11-18).
- **CM-R40** Actions 표 Comment 열(AC-R21의 7번째, 맨 오른쪽): 머리글은 "Comment"(정렬 없음)다.
  - 행마다 말풍선 아이콘 버튼이 있다. 접근 이름은 `canWrite`이면 "Comment 추가", user이면 "Comment 보기"다. 읽지 않은 수가 있으면 뒤에 " (읽지 않은 <N>건)"을 붙인다. 버튼 옆에 숫자 배지(CM-R39)가 있다.
  - 모든 역할에게 보인다.
  - 누르면(Enter·Space 포함) 그 Action의 상세 팝업(AC-R49)이 열린다. `canWrite`이면 Comment 입력 칸에 포커스가 가고 그 칸이 보이게 스크롤한다. user이면 Comment 영역으로 스크롤한다.
  - 행의 다른 곳을 누르면 AC-R48대로 열리고 포커스는 UI-R26을 따른다. 별도 팝업은 없다.
- **CM-R41** Action 상세 팝업의 Comment 영역(AC-R49의 맨 아래, 키·값 줄 다음):
  - 제목은 "Comment (<그 Action Comment 수>)"다.
  - 그 Action의 Comment 목록을 최근순으로 보인다(CM-R33, 연결 Action 상자 없음).
  - 목록 아래 입력 칸(CM-R35)이 있고, 삭제는 CM-R36이다.
  - 예전 Memo 줄은 없다.
  - 요청 중(저장·삭제)에는 팝업의 "닫기"·"삭제"가 꺼지고 Esc를 무시한다(AC-R50과 같음).
- **CM-R42** Action 추가 팝업(AC-R23)에는 Comment 칸(라벨 "Comment", 여러 줄, 선택)이 있다. 등록 요청의 `comment`로 보낸다(AC-R32). Owner가 등록하면 읽음으로, 다른 사람이 등록하면 읽지 않음으로 생긴다.
- **CM-R43** 종료 대화상자(NA-R22)의 글 칸은 "Comment에 남길 내용(선택)"이고, 요청의 `comment`로 보낸다(NA-R30). 성공 뒤 상세 팝업이 열려 있으면 Comment 영역 맨 위에 새 Comment가 보인다.
- **CM-R44** 캐시:
  - Comment 작성·삭제가 성공하면 그 Deal의 Comment 목록, 읽지 않은 수, Deal History와 Deal 목록(모든 조건, 키 `['deals','list']`)을 다시 읽는다(목록 배지 CM-R48, 2026-11-18). Deal 상세 응답은 화면이 이 값을 쓰지 않으므로 다시 읽지 않는다. Action 목록도 다시 읽지 않는다.
  - Action 등록·삭제·상태 변경이 성공하면 기존 무효화(AC·NA)에 Comment 목록과 읽지 않은 수를 더한다.
  - Action 수정이 성공하면 Comment 목록을 다시 읽는다(연결 Action 요약이 바뀐다).
  - 읽음 처리 요청이 끝나면(성공·실패 모두) Comment 목록, 읽지 않은 수와 Deal 목록(`['deals','list']`)만 다시 읽는다.
- **CM-R45** 게이트웨이(`gateway/http`, `comments`): 다음 메서드를 둔다.
  - `list(dealCode, {actionId?})` = `GET /deals/{code}/comments`(actionId가 있을 때만 `action_id` 쿼리)
  - `create(dealCode, {body, actionId})` = `POST /deals/{code}/comments`(actionId가 없으면 `action_id`를 생략)
  - `remove(commentId)` = `DELETE /deal-comments/{id}`(204)
  - `markRead(dealCode, commentIds)` = `POST /deals/{code}/comment-reads`(204)
  - `counts(dealCode)` = `GET /deals/{code}/comment-counts`
  - 응답 매핑: `{id, dealCode, actionId, action: {id, actedOn, progress, nextAction} | null, body, author, createdAt, readAt}`. 집계는 `{unread, byAction: Record<actionId, number>}`다.
  - `update`는 없다. 오류는 서버 상태·문구 그대로다(PL-R39). 삭제 영향 `comment_count`는 `commentCount`로 매핑한다(DD-R40).
- **CM-R46** Fake 게이트웨이(`test/fake/gateway/comments.ts`)는 서버와 같은 규칙·판정 순서·문구를 따른다.
  - CM-R1~R9, R11~R13: 작성·조회·삭제, 최근순, 연결 Action 요약, 권한, 이력 문구.
  - CM-R14·R15: Action 등록 `comment`, 종료 Comment.
  - CM-R16: Action 삭제 때 함께 삭제, 이력 " (Comment <N>건 함께 삭제)".
  - CM-R18: Deal 삭제 때 함께 삭제, `commentCount`.
  - CM-R19: 검색어.
  - CM-R20: 사용자 연결.
  - CM-R26~R29: Owner 읽음, 읽음 처리, 읽지 않은 수.
  - CM-R47: Deal 목록 행·상세의 `unreadCommentCount`(그 Deal의 읽지 않은 Comment 수).
- **CM-R48** Deals 목록 배지(2026-11-18, 화면 `/deals`):
  - 위치: 표 Deal 칸에서 Deal 이름 링크 **바로 오른쪽**, 경고 배지(RK-R15) **앞**이다. 배지는 링크 밖에 있다.
  - 값: 그 행의 `unreadCommentCount`(CM-R47)다. 목록은 Comment 집계 경로(`comments.counts`)를 행마다 부르지 않는다.
  - 표기는 Comments 탭 배지(CM-R39)와 같다. 1 이상일 때만 숫자를 보이고, 100 이상은 "99+"다. 0이면 배지가 없다(공통 함수 `badgeText`, CM-083).
  - 모양은 Comments 탭 배지와 같다(같은 색·크기의 둥근 숫자 배지). 표기 규칙은 탭과 같은 함수(`badgeText`)를 쓰고, 목록 배지는 `shared/ui/CommentBadge.tsx`다(탭 배지 `.tab-badge`와 모양을 맞춘 별도 컴포넌트).
  - 접근 이름은 "읽지 않은 Comment <N>건"이다. N은 실제 수이고 99+로 보여도 실제 수를 쓴다. 마우스를 올리면 같은 문구(title)가 보인다.
  - 배지는 누를 수 없다(링크·버튼 아님, Tab 순서에 들지 않음). Deal 이름 링크의 접근 이름은 Deal 이름 그대로다.
  - 모든 역할(admin·sales·user)에게 같게 보인다. 빠른 보기·인라인 편집·정렬 머리글·열 순서는 바뀌지 않는다.

### 2.8 오류와 메시지

| 상황 | 상태·type | 문구 |
| --- | --- | --- |

| 본문 비었음(작성) | 422 `invalid-value` | Comment를 입력하세요. |
| 연결 Action이 이 Deal에 없음 | 422 `invalid-value` | 선택한 Action이 이 Deal에 없습니다. |

## 3. Business use case

### CM-UC1 Deal Comment 쓰기
- 행위자: sales·admin
- 사전 조건: 로그인, Deal이 있다
- 기본 흐름: `POST /deals/{code}/comments` `{body}` → 201, 응답 `action_id` null, History "Comment" 1건(CM-R3~R6, R13)
- 예외: 본문 빈 값·NUL 422, 없는 Deal 404, user 403
- 결과: Deal Comment 1건과 History 1건

### CM-UC2 Action Comment 쓰기
- 행위자: sales·admin(남의 Action에도)
- 사전 조건: 그 Deal의 Action이 있다
- 기본 흐름: `POST /deals/{code}/comments` `{body, action_id}` → 201, History "Action Comment (<수행일> <유형>)" 1건
- 예외: 다른 Deal의 Action·없는 Action 422(CM-R5)
- 결과: 같은 Deal 소속이면서 Action에 연결된 Comment 1건

### CM-UC3 (폐지 2026-11-17) Comment 수정 — 수정 기능 없음(CM-R10)
- 수정 유스케이스·`PUT /deal-comments/{id}` 경로는 없다. PUT 요청은 405이고 Comment는 그대로다(CM-057). 잘못 쓴 Comment는 삭제(CM-UC4) 뒤 다시 쓴다.

### CM-UC4 Comment 삭제
- 행위자: 작성자 sales, admin
- 기본 흐름: `DELETE /deal-comments/{id}` → 204, History "삭제" 1건(CM-R11)
- 예외: 남의 Comment 403, 없음 404

### CM-UC5 Comment 조회
- 행위자: 로그인한 모든 역할
- 기본 흐름: `GET /deals/{code}/comments`(선택 `action_id`) → 최근순 목록(연결 Action 요약·읽음 시각 포함), `GET /deal-comments/{id}` → 한 건(CM-R7~R9)

### CM-UC6 Action을 등록하며 Comment 남기기
- 행위자: sales·admin
- 기본 흐름: `POST /deals/{code}/actions`에 `comment` → Action과 Action Comment가 한 번에 저장, History는 Action 등록 → Comment 등록 순(CM-R14)
- 예외: Comment NUL 422, 등록이 다른 이유로 거절되면 Comment도 없음

### CM-UC7 Next Action을 종료하며 Comment 남기기
- 행위자: Action 작성자 sales, admin
- 기본 흐름: `PUT /deal-actions/{id}/next-action-status` `{status: done|not_done, comment}` → 상태 변경과 Action Comment 1건, History는 Next Action 줄 → Comment 등록 줄(CM-R15)
- 예외: Open + Comment 422, 같은 상태 409(Comment 없음)

### CM-UC8 Action·Deal 삭제와 Comment
- 행위자: Action 삭제 권한자(AC-R17), Deal 삭제 권한자(DD)
- 기본 흐름: Action을 지우면 그 Action Comment가 함께 지워지고 이력에 건수가 붙는다(CM-R16). Deal을 지우면 그 Deal 소속 Comment가 모두 지워지고 삭제 영향에 `comment_count`가 나온다(CM-R18)

### CM-UC9 기존 Memo 이전과 컬럼 제거(배포)
- 행위자: 배포(local·dev 자동, product는 사람 승인)
- 기본 흐름: `alembic upgrade head` → Memo가 있는 Action마다 Action Comment 1건 → 건수 점검 → `memo` 컬럼 drop(CM-R21~R23)
- 예외: 건수가 맞지 않으면 중단하고 아무것도 바뀌지 않음
- 결과: 기존 Memo가 Action Comment로 보이고 `memo` 컬럼은 없다

### CM-UC10 Deal Owner가 받은 Comment 확인
- 행위자: Deal Owner(sales)
- 사전 조건: 다른 사람이 Owner의 Deal에 Comment를 남겼다
- 기본 흐름:
  1. Deal 상세를 연다. Comments 탭 배지와 Actions 표 행 배지에 읽지 않은 수가 보인다.
  2. Comments 탭이나 Action 상세 팝업을 연다.
  3. 표시된 읽지 않은 Comment가 읽음 처리된다(204). 배지가 줄고 "NEW" 표시가 남는다(CM-R26~R29, R33, R38, R39).
- 대안: Owner가 아닌 사람이 열면 읽음 처리하지 않는다. 배지와 "읽지 않음" 표시는 모두에게 그대로 보인다.
- 예외: 읽음 처리가 실패하면 배지가 그대로 남고 다음 열람에서 다시 보낸다.

### CM-UC11 Comments 탭에서 보기·쓰기·지우기
- 행위자: 보기는 모든 역할, 쓰기는 sales·admin, 삭제는 작성자 sales·admin
- 기본 흐름: "Comments" 탭을 연다. 최근순 목록을 본다(Action Comment는 연결 Action 요약과 "Action 보기"). 목록 아래 입력 칸에 쓰고 Enter나 "저장"을 누른다. Deal Comment가 목록 맨 위에 생긴다(CM-R32~R36).
- 대안: "Action 보기"를 누르면 Actions 탭으로 가서 그 Action 상세 팝업이 열린다(CM-R37). "삭제"는 확인을 거친다.

### CM-UC12 Action에서 Comment 보기·쓰기
- 행위자: 보기는 모든 역할, 쓰기는 sales·admin(남의 Action 포함)
- 기본 흐름: Actions 표의 Comment 아이콘을 누른다. Action 상세 팝업이 열리고 맨 아래에 그 Action의 Comment 목록과 입력 칸이 있으며 입력 칸에 포커스가 간다. 쓰고 저장하면 그 Action의 Comment가 된다(CM-R40, R41, R35).

### CM-UC13 Deals 목록에서 읽지 않은 Comment 확인
- 행위자: 로그인한 모든 역할(주로 Deal Owner sales)
- 사전 조건: 다른 사람이 Deal에 Comment를 남겼다
- 기본 흐름: Deals 목록을 연다. 읽지 않은 Comment가 있는 Deal은 이름 바로 오른쪽에 배지(수)가 보인다. 이름을 눌러 상세에서 Comments 탭을 연다(Owner면 읽음 처리, CM-R38). 목록으로 돌아오면 배지가 사라져 있다(CM-R47·R48·R44).
- 대안: Owner가 아닌 사람이 상세를 열면 읽음 처리하지 않으므로 목록 배지가 그대로다.
- 예외: 목록을 읽지 못하면 DL-R18의 오류 배너다(배지만 따로 실패하지 않는다).
- 결과: 목록에서 어느 Deal에 읽지 않은 Comment가 몇 건인지 안다.
