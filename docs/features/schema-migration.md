## 1. 개요

- 목적: 앱 DB 스키마를 **하나의 기준선 리비전**에서 시작해 Alembic 마이그레이션으로만 만들고 바꾸며, 모든 테이블이 따르는 공통 규칙(PK·FK·사용자 참조·제약 이름)과 마이그레이션 작성 원칙(기존 데이터 삭제 금지, expand/contract)을 정한다.
- 사용자(행위자): 운영자·배포 도구(`alembic upgrade head`를 실행하는 쪽 — local·dev는 `scripts/start-backend.sh`, product는 Jenkins `Deploy: Product`의 `infra/docker/deploy.sh` migrate 컨테이너), 개발자(새 리비전 작성), 앱(새 행 id 할당). 앱 역할(admin·sales·user)과 HTTP API는 없다.
- 범위
  - 기준선 리비전 `00c3126aa926`(파일 `20261105_00c3126aa926_baseline.py`): 빈 DB에 현재 스키마(앱 테이블 26개)와 기본 시드를 만든다, downgrade 거부
  - 리비전 그래프(base·head·부모), head에서 재실행, 그래프에 없는 리비전이 남은 DB
  - head 스키마 = ORM 메타데이터
  - 공통 스키마 규칙: id(BIGINT identity) PK와 예외, FK 타입 일치, FK ON DELETE(RESTRICT 기본·CASCADE 허용 목록), FK 선행 인덱스, 사용자 참조, 소프트 삭제 컬럼 위치, 제약 이름 규칙
  - 앱이 미리 받는 id(`IdAllocator` Port)의 계약
  - 마이그레이션 작성·적용 원칙(규칙으로만, 2.3 SC-R8~R10)
- 범위 밖
  - 테이블별 컬럼·CHECK·인덱스·유니크(각 소유 feature 2.2와 `tests/unit/infra/schema/test_<테이블>_schema.py`, 예: `test_license_contract_schema.py` → LC)
  - 기본 시드 항목의 화면·API 동작(잠금·순서 변경·삭제 등): 코드는 CD, BANT Label·Action 유형은 CL. API로 보이는 기본값 순서·필드는 CD-001·CL-001·CL-025(2026-11-10 결정), 시드 값 자체는 SC
  - 사용자 연결 탐지(퇴사 처리 판단, `tests/support/user_links.py`의 연결 목록 의미): US
  - API의 id 표현(JSON 정수·범위 밖 422·경로 파라미터): PL
  - product 적용 승인·`pg_dump`·배포 롤백 절차(사람 승인, `docs/dev-guide.html` 16장), 하네스 `guard.py`의 product 대상 alembic 거부, `start-backend.sh`·`deploy.sh` 스크립트 테스트(하네스·배포 도구, feature 아님)
  - 경쟁·동시성(시퀀스 동시 호출 등)
- 관련 화면·메뉴: 없음

### 2.3 비즈니스 규칙

리비전 그래프와 기준선
- **SC-R1** 리비전 그래프의 base는 기준선 `00c3126aa926` 하나이고 head도 하나다. 기준선은 `down_revision`이 None이고 `branch_labels`·`depends_on`이 없다. 기준선 파일 이름은 `20261105_00c3126aa926_baseline.py`이고, 새 리비전 파일 이름은 `alembic.ini`의 `file_template`(`YYYYMMDD_<rev>_<slug>.py`)을 따른다. 지금 그래프에는 리비전이 5개 있다: 기준선 → 날짜 전환 리비전 `b4d7e2a9c613`(파일 `20261113_b4d7e2a9c613_business_dates.py`, SC-R20) → 사용자 컬럼 정리 리비전 `c8e3f1a7d295`(파일 `20261113_c8e3f1a7d295_drop_user_creator_and_reason.py`, SC-R21) → Deal Vendor 필수 리비전 `e6b1d4f8a302`(파일 `20261113_e6b1d4f8a302_deal_vendor_required.py`, SC-R22) → Deal Product 이름 변경 리비전 `a9d3f5c7e214`(파일 `20261116_a9d3f5c7e214_deal_solution_to_product.py`, SC-R23).
- **SC-R2** 빈 DB에 `alembic upgrade head`를 실행하면 앱 테이블 26개(2.2)와 `alembic_version`만 생기고 `alembic_version.version_num`은 head인 `a9d3f5c7e214`이다. 마이그레이션은 한 트랜잭션으로 적용된다(`env.py`의 `context.begin_transaction()`).
- **SC-R3** 기준선 upgrade 직후 `codes` 13행·`bant_labels` 23행·`action_types` 8행(2.2의 값)이 있고 나머지 앱 테이블 23개는 0행이다. 시드 값(키·이름·순서·outcome·확률 힌트·구분·기본 여부·만든 사람 NULL)은 Fake 시드와 같다.
- **SC-R4** 기준선은 되돌릴 수 없다. 기준선의 `downgrade()`는 DB를 건드리기 전에 `RuntimeError` "최초 리비전(00c3126aa926)은 되돌릴 수 없습니다. 빈 DB가 필요하면 DB를 새로 만드세요."를 낸다. head인 DB에 `alembic downgrade base`를 실행하면 Deal Product 이름 변경 리비전, Deal Vendor 필수 리비전, 사용자 컬럼 정리 리비전, 날짜 전환 리비전을 차례로 되돌린 뒤 기준선에서 이 오류로 중단된다. 전체가 한 트랜잭션이라(SC-R2) `alembic_version`(head)과 테이블·컬럼은 그대로다. 빈 DB가 필요하면 DB를 새로 만든 뒤 `upgrade head`를 실행한다.
- **SC-R5** 이미 head인 DB에 `upgrade head`를 다시 실행하면 아무것도 바뀌지 않는다: 모든 앱 테이블의 열(형식·NOT NULL·기본값)·제약(PK·UNIQUE·CHECK·FK 정의)·인덱스 정의와 행 수가 같고 `alembic_version`은 그대로다(시드가 두 번 들어가지 않음).
- **SC-R6** `alembic_version`에 그래프에 없는 리비전 id(퇴역 리비전)가 남은 DB에 `upgrade head`를 실행하면 Alembic `CommandError`로 실패하고 스키마·`alembic_version`은 바뀌지 않는다. 이런 DB(통합 전 head보다 뒤처진 local·dev DB)는 새로 만든다. 통합 전 head(`00c3126aa926`)였던 DB는 같은 id라 그대로 쓰고, `upgrade head`가 날짜 전환·사용자 컬럼 정리·Deal Vendor 필수·Deal Product 이름 변경 리비전을 차례로 적용한다.
- **SC-R7** head 스키마는 ORM 메타데이터(`app.infra.db.models`가 등록한 `Base.metadata`)와 같다: head를 적용한 DB와 메타데이터를 Alembic `compare_metadata`(`compare_type=True`)로 비교한 차이가 0건이다. 스키마를 바꾸는 개발자는 ORM 모델과 리비전을 함께 바꾼다.

마이그레이션 작성·적용 원칙
- **SC-R8** 기존 데이터 삭제 금지(2026-11-05 사용자 지시): 리비전의 `upgrade`는 기존 행·컬럼 값을 지우거나 버리지 않는다 — `DELETE`·`TRUNCATE`, 데이터가 있을 수 있는 테이블·컬럼 drop, 값을 버리는 타입 변경·덮어쓰기 금지. 없애야 하면 데이터를 새 위치로 옮기는 expand 리비전과 사람이 승인한 contract 리비전으로 나누고, 데이터 손실 가능성이 있으면 구현 전에 사용자에게 묻는다. 2026-10-15의 "보존 데이터 없음"·이후의 "expand/contract 원칙의 예외" 결정은 적용하지 않는다. 검증: 기준선의 upgrade 본문(docstring 제외)에는 `delete`·`truncate`·`update`(단어)·`drop_table`·`drop_column`·`op.execute`가 없다(자동 검사, SC-011). 새 리비전은 리뷰가 검사하고 위반은 Blocker다(자동 검사 없음, 확인 필요 Q4). 날짜 전환 리비전 `b4d7e2a9c613`의 timestamptz 컬럼 drop은 2026-11-13 사용자가 승인한 contract다(SC-R20). 시각만 버리고 행과 날짜는 남는다. 사용자 컬럼 정리 리비전 `c8e3f1a7d295`의 `users.created_by_user_id` drop도 2026-11-13 사용자가 승인한 contract이고, `users.delete_reason` drop은 같은 정보가 `deleted_at`에 남아 손실이 없다(SC-R21). Deal Product 이름 변경 리비전 `a9d3f5c7e214`은 열 이름만 바꿔 행·값을 지우거나 바꾸지 않는다(SC-R23).
- **SC-R9** 하위 호환(expand/contract): product 배포가 실패하면 `deploy.sh`는 앱 코드(이전 이미지 태그)만 되돌리고 마이그레이션은 되돌리지 않으므로, 리비전은 **이전 앱 코드가 새 스키마에서 계속 동작하도록** 쓴다(새 테이블, NULL 허용·기본값 있는 컬럼 추가, 데이터 복사). 구 앱과 공존할 수 없는 변경은 contract 단계로 미루고 사람 승인을 받는다. 계획 단계(feature-planner)는 리비전마다 "필요 여부, 하위 호환 여부, 기존 데이터 보존 방법"을 적는다. 검증: 계획·리뷰(자동 검사 없음).
- **SC-R10** 적용 경로: local·dev는 `./scripts/start-backend.sh --profile local|dev`가 시작 전에 그 프로파일 DB에 `alembic upgrade head`를 실행한다(`--skip-migrate`로 생략). local·dev의 `downgrade`·`stamp`는 확인 없이 실행할 수 있다. product는 사람이 승인한 Jenkins `Deploy: Product`에서만 `deploy.sh`가 `pg_dump` 백업 뒤 migrate 컨테이너로 적용하며, 하네스는 Claude의 product 대상 alembic 명령을 거부한다. 검증: 하네스·배포 도구 테스트(feature 밖).

공통 스키마 규칙(id)
- **SC-R11** 대리 키 테이블 19개(2.2)의 PK는 `id BIGINT GENERATED BY DEFAULT AS IDENTITY`(시작 1, 증가 1, 최대 9,007,199,254,740,991 = 2^53−1 = `app.domain.common.ids.MAX_ID`), NOT NULL, PK 컬럼은 `id` 하나다. `BY DEFAULT`이므로 앱이 미리 받은 id로도, id를 생략한 DB 기본값으로도 넣을 수 있다. 날짜 전환 리비전
- **SC-R20** 리비전 `b4d7e2a9c613`(부모 `00c3126aa926`, 파일 `20261113_b4d7e2a9c613_business_dates.py`)은 업무 날짜 컬럼 4개를 date로 바꾼다(2026-11-13 사용자 결정).

  - 채우기: 옛 값을 업무 시간대로 바꾼 날짜다. 업무 시간대는 마이그레이션을 실행하는 프로세스의 OS 로컬 시간대다(TM-R4). Python `astimezone().date()`로 계산하고 SQL `AT TIME ZONE`은 쓰지 않는다. DB 세션 시간대가 앱과 다를 수 있기 때문이다. 옛 값이 null이면 새 값도 null이다.
  - 점검: 테이블 행 수가 채우기 전과 같아야 하고, 옛 값이 있던 행은 모두 새 값이 있어야 한다. 하나라도 어기면 `RuntimeError`로 중단한다. 트랜잭션이 롤백되므로 아무것도 지워지지 않는다.

    - `ck_deal_actions_next_action_closed_at` → `ck_deal_actions_next_action_closed_on`
    - `ck_license_contracts_ended_has_time` → `ck_license_contracts_ended_has_date`(조건은 같음)
    - `ix_deal_actions_acted_at`·`ix_deal_actions_deal_id_acted_at` → `ix_deal_actions_acted_on`·`ix_deal_actions_deal_id_acted_on`
  - 버리는 정보: 시각뿐이고 행과 날짜는 남는다. SC-R8의 contract 예외로 사용자가 승인했다.
  - downgrade: 옛 timestamptz 컬럼을 되살려 날짜의 업무 시간대 00:00으로 채운다. 원래 시각은 돌아오지 않는다. NOT NULL·CHECK·인덱스도 되돌리고 새 컬럼을 drop한다.
  - 하위 호환(SC-R9 예외, 사용자 승인): 코드만 되돌리면 구 앱은 옛 컬럼이 없어 실패한다. 롤백할 때는 `downgrade -1`을 함께 실행하거나 배포 전에 받아 둔 `pg_dump`로 복원한다. product 적용은 사람 승인을 받고 배포 전 `pg_dump`를 마친 뒤에만 한다.

## 3. Business use case

### SC-UC1 빈 DB를 현재 스키마로 만든다
- 행위자: 운영자·배포 도구(`start-backend.sh`, product migrate 컨테이너)
- 사전 조건: 테이블이 없는 빈 DB
- 기본 흐름: `alembic upgrade head` → 기준선이 테이블 26개를 만들고 기본 시드를 넣고, 뒤 리비전들이 차례로 적용되어 `alembic_version`을 head로 기록한다(한 트랜잭션)
- 대안·예외 흐름: 이미 head인 DB면 아무것도 하지 않는다(SC-R5). 퇴역 리비전이 남은 DB면 실패하고 바뀌지 않는다(SC-R6) → 운영자가 DB를 새로 만든 뒤 다시 실행
- 결과: head 스키마(ORM과 같음, SC-R7)와 기본 시드만 있는 DB

### SC-UC2 기준선을 되돌리려 한다
- 행위자: 운영자(local·dev)
- 사전 조건: head인 DB
- 기본 흐름: `alembic downgrade base` → 기준선 `downgrade()`가 아무것도 바꾸기 전에 거부한다
- 결과: 스키마·데이터·`alembic_version` 그대로. 빈 DB가 필요하면 DB를 새로 만든다

### SC-UC3 개발자가 스키마를 바꾼다
- 행위자: 개발자(계획 feature-planner, 구현 infra-engineer, 리뷰 code-reviewer)
- 사전 조건: head = ORM(SC-R7)
- 기본 흐름: ORM 모델을 바꾸고 기준선 head 뒤에 새 리비전을 하나 붙인다(SC-R1) → 리비전은 공통 스키마 규칙(SC-R11~R18)과 원칙(SC-R8·R9)을 따른다 → 다시 head = ORM
- 대안·예외 흐름: 기존 데이터를 지워야 하는 변경은 expand 리비전과 사람이 승인한 contract 리비전으로 나누고, 손실 가능성은 구현 전에 사용자에게 묻는다
- 결과: 그래프는 head 하나, 스키마 점검 위반 0건, product 적용은 사람 승인 뒤(SC-R10)

### SC-UC4 앱이 새 행의 id를 미리 받는다
- 행위자: 앱(유스케이스가 `uow.ids.next_id(kind)` 호출)
- 사전 조건: head인 DB(또는 Fake)
- 기본 흐름: 종류의 시퀀스에서 다음 id를 받아 엔티티를 만들고 그 id로 insert한다
- 대안·예외 흐름: 작업 단위가 롤백되면 받은 번호는 버려진다(재사용 없음)
- 결과: 1~2^53−1 범위의, 같은 테이블의 DB 기본값 id와 겹치지 않는 id

### SC-UC5 기존 DB의 사용자 등록자·퇴사 사유 컬럼을 없앤다
- 행위자: 운영자·배포 도구
- 사전 조건: `b4d7e2a9c613`인 DB(사용자·퇴사자 행이 있을 수 있음), product는 사람 승인과 `pg_dump` 완료
- 기본 흐름: `alembic upgrade head` → 사용자 컬럼 정리 리비전이 FK·인덱스·CHECK와 두 컬럼을 drop한다(SC-R21)
- 대안·예외 흐름: 배포 롤백이 필요하면 `downgrade -1`로 스키마를 되돌린다(등록자는 자기 자신으로 채워짐) 또는 `pg_dump` 복원
- 결과: 사용자 행 수·`deleted_at` 값은 그대로이고 두 컬럼만 없다

### SC-UC6 Deal Vendor 필수 리비전을 적용한다
- 행위자: 운영자·배포 도구(SC-R10)
- 사전 조건: DB가 `c8e3f1a7d295`
- 기본 흐름: `upgrade head` → 사전 점검 통과 → `deals.vendor_id` NOT NULL → `alembic_version` = `e6b1d4f8a302`
- 예외: Vendor 없는 Deal이 있으면 건수·code 문구로 중단, 아무것도 바뀌지 않음 → 사람이 그 Deal들에 Vendor를 지정한 뒤 다시 실행
- 결과: 모든 Deal이 Vendor를 가진 스키마(행·값 그대로)

### SC-UC7 Deal Product 이름 변경 리비전을 적용한다
- 행위자: 운영자·배포 도구(SC-R10)
- 사전 조건: DB가 `e6b1d4f8a302`, product는 사람 승인과 `pg_dump` 완료
- 기본 흐름: `upgrade head` → `deals.solution`이 `deals.product`로 바뀜 → `alembic_version` = `a9d3f5c7e214`
- 대안·예외 흐름: 배포 롤백이 필요하면 코드 롤백과 함께 `downgrade -1`(손실 없음) 또는 `pg_dump` 복원
- 결과: 모든 Deal의 Product 값이 이름 변경 전 Solution 값과 같다

- Then `down_revision`은 `b4d7e2a9c613`이고, `branch_labels`는 비어 있으며, 파일 경로는 `20261113_c8e3f1a7d295_drop_user_creator_and_reason.py`로 끝난다. `downgrade` 함수가 있다

### SC-041 사용자 컬럼 정리 upgrade는 사용자 행·퇴사 시각을 그대로 두고 두 컬럼과 FK·인덱스·CHECK만 없앤다
- Given 빈 임시 DB를 `b4d7e2a9c613`까지 올리고, 자기 자신이 등록자인 admin root, root가 등록한 재직 sales kim, root가 등록하고 퇴사한 lee(`deleted_at`·`delete_reason='resigned'`), kim이 Owner인 Deal 하나를 넣고 `users`의 (id, login_id, role, deleted_at) 목록을 기록했다
- When `upgrade head`를 실행한다
- Then `alembic_version`은 `c8e3f1a7d295`이고 `users`의 (id, login_id, role, deleted_at) 목록이 기록과 같다(행 수 3)
- And `users`에 `created_by_user_id`·`delete_reason` 컬럼, FK `fk_users_created_by_user_id_users`, 인덱스 `ix_users_created_by_user_id`, CHECK `ck_users_delete_reason_valid`·`ck_users_deleted_pair`가 없다
- And Deal의 `owner_user_id`는 kim 그대로다

### SC-042 사용자 컬럼 정리 downgrade는 등록자를 자기 자신으로, 퇴사 사유를 deleted_at으로 채워 이전 스키마로 되돌린다
- Given SC-041처럼 head까지 올린 임시 DB(재직 2명, 퇴사 1명)
- When `downgrade -1`을 실행한다
- Then `alembic_version`은 `b4d7e2a9c613`이고 사용자 행 수는 3이다
- And 모든 행의 `created_by_user_id`는 자기 `id`이고 NOT NULL이며, FK `fk_users_created_by_user_id_users`(RESTRICT)와 인덱스 `ix_users_created_by_user_id`가 있다
- And `delete_reason`은 퇴사한 lee만 `'resigned'`이고 나머지는 NULL이며, CHECK `ck_users_delete_reason_valid`·`ck_users_deleted_pair`가 있다
- And 그 상태에서 `upgrade head`를 다시 하면 SC-041의 결과와 같다

### SC-043 사용자 컬럼 정리 upgrade 본문에는 행을 지우거나 바꾸는 문장이 없고 drop_column은 두 컬럼뿐이다
- Given 리비전 `c8e3f1a7d295` 모듈 소스의 `upgrade` 함수 본문(docstring 제외, 소문자)
- When 금지 토큰과 `drop_column` 호출을 찾는다
- Then `\bdelete\b`·`\btruncate\b`·`\bupdate\b`·`drop_table`·`op\.execute`가 없고, `drop_column` 호출은 `users`의 `created_by_user_id`·`delete_reason` 두 개뿐이다

### SC-044 Deal Vendor 필수 리비전은 사용자 컬럼 정리 리비전을 부모로 하고 정해진 파일 이름이며 downgrade 함수가 있다
- When 리비전 그래프를 읽는다
- Then `e6b1d4f8a302`의 부모는 `c8e3f1a7d295`, 파일 이름은 `20261113_e6b1d4f8a302_deal_vendor_required.py`이고 `downgrade` 함수가 있다(head 여부는 SC-049)

### SC-045 Vendor가 모두 있는 DB의 upgrade는 행·값을 그대로 두고 vendor_id를 NOT NULL로 만든다
- Given `c8e3f1a7d295`인 DB에 Vendor SAP와 SAP를 고른 Deal 2건
- When `upgrade e6b1d4f8a302`를 실행한다
- Then `alembic_version`은 `e6b1d4f8a302`, `deals.vendor_id`는 NOT NULL이고 Deal 2건의 모든 열 값이 전과 같다. 이어서 `vendor_id` 없이 `deals`에 insert하면 `IntegrityError`(NOT NULL 위반)다

### SC-046 Vendor 없는 Deal이 있으면 upgrade가 건수·code 문구로 중단되고 스키마·행이 그대로다
- Given `c8e3f1a7d295`인 DB에 Vendor 있는 Deal 1건과 Vendor 없는 Deal 2건(code A < B)
- When `upgrade e6b1d4f8a302`를 실행한다
- Then `RuntimeError` 문구에 "2건"과 "A, B"가 있고 `alembic_version`은 `c8e3f1a7d295`, `vendor_id`는 NULL 허용이며 Deal 3건의 값이 그대로다

### SC-047 Deal Vendor 필수 downgrade는 NOT NULL만 풀고 행·값이 그대로다
- Given `e6b1d4f8a302`인 DB에 Vendor SAP인 Deal 1건
- When `downgrade -1`을 실행한다
- Then `alembic_version`은 `c8e3f1a7d295`, `vendor_id`는 NULL 허용이고 Deal 값이 그대로다

### SC-048 Deal Vendor 필수 upgrade 본문에는 행·컬럼을 지우거나 바꾸는 문장이 없다
- When 리비전 파일의 `upgrade` 본문을 읽는다
- Then `DELETE`·`UPDATE`·`TRUNCATE`·`drop_column`·`drop_table`이 없다

### SC-049 Deal Product 이름 변경 리비전은 Vendor 필수 리비전을 부모로 하고 정해진 파일 이름이며 head이고 downgrade 함수가 있다
- When 리비전 그래프를 읽는다
- Then `a9d3f5c7e214`의 부모는 `e6b1d4f8a302`, 파일 이름은 `20261116_a9d3f5c7e214_deal_solution_to_product.py`, head는 `a9d3f5c7e214` 하나이고 `downgrade` 함수가 있다

### SC-050 Product 이름 변경 upgrade는 행·값을 그대로 두고 deals.solution을 deals.product로 바꾼다
- Given `e6b1d4f8a302`인 DB에 `solution` 값이 "ITDR"·""(빈 값)인 Deal 2건
- When `upgrade head`를 실행한다
- Then `alembic_version`은 `a9d3f5c7e214`, `deals`에 `solution` 열이 없고 `product`가 `varchar(200) NOT NULL`이며, 두 Deal의 `product`는 "ITDR"·""이고 다른 열 값과 행 수가 전과 같다

### SC-051 Product 이름 변경 downgrade는 열 이름만 solution으로 되돌리고 값이 그대로다
- Given head인 DB에 `product` "ITDR"인 Deal 1건
- When `downgrade -1`을 실행한다
- Then `alembic_version`은 `e6b1d4f8a302`, `deals.solution`이 "ITDR"이고 `product` 열이 없으며 행 수가 같다

### SC-052 Product 이름 변경 upgrade 본문에는 행·컬럼을 지우거나 바꾸는 문장이 없고 열 이름 변경 하나뿐이다
- When 리비전 파일의 `upgrade` 본문(docstring 제외)을 읽는다
- Then `\bdelete\b`·`\btruncate\b`·`\bupdate\b`·`add_column`·`drop_column`·`drop_table`·`op\.execute`가 없고, `alter_column` 호출은 `deals`의 `solution` → `product` 하나뿐이다
