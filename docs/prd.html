1. 개요

1.1 목적

Deal을 등록하고 진행 상태를 추적하며 Next Action과 Forecast를 관리한다. 경영·영업 관점의 Dashboard에서 Pipeline과 Closing 가능성을 즉시 확인한다.

핵심 관리 질문: “어떤 Deal이 있고 → 현재 어느 단계이며 → 다음 Action은 무엇이고 → 언제 얼마가 Closing 될 것인가?”
Deal 등록 → Status 진행 → Next Action → Forecast → Closing → 분석

1.2 설계 원칙

  • Deal 중심 원장: 연락처(고객·파트너)·Status·Forecast·Action을 하나의 Deal 원장에 연결한다.
  • 메뉴 단순화: 사용자 메뉴는 Dashboard / Deals / Forecast / Reports 4개로 고정한다. Admin은 사용자 메뉴에서 별도 접근한다.
  • 입력 최소화: 영업담당자가 1~2분 안에 상태와 Next Action을 업데이트할 수 있어야 한다. 추적·경고·집계는 시스템이 자동 처리한다.
  • 의미 분리: Status(진행 단계), Forecast(Closing 판단, Won/Lost 포함)를 독립된 값으로 관리한다.
  • 데이터 일치: Deal 원장, Forecast, Dashboard의 금액과 건수가 항상 같아야 한다.

5.6 연락처 관리 (Contact Management, 확정)

고객과 파트너 정보는 명함처럼 관리한다. 한 사람의 연락처가 한 행이며, 고객사 + 담당자(이름·직급·이메일·전화 등)를 함께 저장한다. 고객사에 담당자가 2명이면 2행이 저장된다. 고객과 파트너는 하나의 테이블에 두고 구분자(고객/파트너)로만 나눈다.

항목설명
구분고객 또는 파트너
회사명 · 담당자명공백(space)을 넣을 수 없다. 입력란에서 공백 입력을 막고, 서버도 공백이 있으면 거부한다. 대소문자는 같은 표기로 본다(Acme = ACME)
직급 · 이메일 · 전화연락처 정보. 이메일과 전화도 공백을 넣을 수 없다. 동명이인은 이메일로 구분한다. 이메일은 없어도 되며, 이메일 없이 입력하면 같은 회사명+담당자명의 기존 연락처와 같은 사람으로 본다
직원수연락처에 두지 않는다. 사용자 수(Users)는 견적 단위이므로 Deal 정보로 입력한다(5.1절)

Deal과 연결

  • 고객: Deal은 고객 연락처 1건을 참조한다. Deal 생성 시 반드시 입력하며 최소 회사명과 담당자명까지는 필수이다.
  • 파트너: Deal과 파트너는 1:N이다. 다만 실제로 영업을 진행 중인 활성(active) 파트너는 한 곳이다. 파트너는 선택이며(파트너 없는 Deal 허용), 입력하는 경우 회사명과 담당자명은 필수이다. 여러 건이 생기는 경우는 기존 파트너가 교체될 때뿐이며, 교체되면 이전 파트너는 비활성이 되어 이력으로 남는다. 화면에는 활성 파트너만 보여준다. 파트너 교체는 Deal History에 기록한다.

화면 흐름 (Deal 등록·수정·상세 화면)

  1. 회사명 선택: 기존 연락처에서 회사명을 distinct로 찾아 목록으로 보여주고 선택한다. 신규 회사면 직접 입력한다.
  2. 담당자 선택: 선택한 회사의 담당자를 목록으로 보여준다(3명이면 3명). 신규 담당자면 직접 입력한다.
  3. 자동 입력: 기존 담당자를 선택하면 그 담당자의 연락 정보가 입력란에 자동으로 채워진다.
  4. 수정 반영: 연락 정보가 바뀌었으면 입력란을 직접 고쳐 저장한다. 이후에는 고친 내용이 연락처(명함) 데이터에 갱신되어 다음에 선택할 때 그 값으로 나온다.

전체 관리: admin은 Admin > Settings > contacts 관리에서 등록된 모든 연락처(고객·파트너)를 생성·조회·수정·삭제할 수 있다. Deal에 연결된 연락처는 삭제할 수 없다(409).

연락처 한 행은 여러 Deal이 공유하므로, 연락처를 수정하면 그 연락처를 참조하는 모든 Deal에 같은 값이 보인다. 현재는 고객·파트너가 별도 테이블이고 별도 화면에서 등록한다. 기존 데이터를 연락처로 옮기는 마이그레이션이 필요하다. 예정

6.3 Open / Won / Lost

Won/Lost는 Forecast 코드이며, Won/Lost가 아닌 Forecast(Pipeline / Best / Most Likely / Commit)는 Open이다. Won/Lost Deal은 Open Pipeline에서 제외한다(R06). Result 속성은 현재 단계에서 두지 않는다. Deal의 결과는 Forecast(Won/Lost)로 판단한다. Forecast가 Lost가 되어도 Status는 그대로 둔다. 따라서 Status의 lost 값은 없애고, 기존 lost 단계 Deal은 Forecast=Lost로 옮기고 Status는 단계 이력의 직전 단계로 되돌린다(데이터 이전 마이그레이션 필요, 승인 대상).

6.6 매출일 = Expected Close (확정)

revenue_date 하나가 매출일이자 Expected Close 날짜다. Deal이 진행 중이면 예상 매출일(Expected Close)이고, Deal이 성공(Won)하면 최종 매출일자로 갱신한다. Deal이 실패(Lost)하면 값을 바꾸지 않아 마지막 Expected Close가 그대로 남는다. 기간 집계(R01)는 이 값을 기준으로 한다.

6.7 Status와 Forecast의 관계 (확정)

Status와 Forecast는 별개의 정보다. Won과 계약완료만 같은 것으로 취급한다. 두 값은 시스템 내부 고유 코드 값으로 연결되므로 이름을 바꿔도 규칙이 유지된다(CM-07).

Forecast를 Lost로 변경Status는 그대로 둔다

  • Won 이후에도 잠그지 않는다. 종결된 Deal도 Forecast·Status를 포함한 모든 정보를 수정할 수 있다. 수정한 내용은 빠짐없이 Deal History에 기록한다.
  • 되돌릴 때 이미 입력된 매출금액·매출일 등 나머지 정보는 그대로 둔다.
  • 그 외 Deal 정보(금액, 매출일, 담당자, 연락처, Label, Action, 파일 등)는 Deal의 상태와 상관없이 언제든 수정할 수 있다.
