## 반드시 지킬 규칙 (요약)
- 계층: web → application → domain, infra → application → domain. application은 infra를 import하지 않고
  외부 통신은 application/ports 의 Port(Protocol)로만 한다. infra가 Port를 구현한다.
- backend의 .py 파일은 300줄 이하. 초과하면 책임별로 분리한다(줄이기 위한 압축 금지).
- 모든 공개 함수에 타입 힌트, mypy strict 통과. 함수 복잡도·인자 수는 ruff 설정을 따른다.
- 프로파일은 local/dev/product. 설정은 app.config.get_settings()로만 읽고, domain/application에서 import하지 않는다.
- 비밀과 .env는 읽지도 쓰지도 않는다. 의존성 추가(uv add)는 사용자 승인 후에만 한다.
- DB 마이그레이션: local과 dev는 자동(dev는 main 머지 시 Jenkins 배포가 alembic upgrade head 실행),
  product만 사람 승인 후 deploy.sh가 실행. dev에 자동 적용되므로 항상 하위 호환(expand/contract)으로 작성한다.
  downgrade/stamp는 사용자 확인, product 대상 alembic은 거부. 배포·머지·push는 사람이 한다.

6. Subagent(Agent) 설계

6.1 분리 원칙

  • 계층 경계가 곧 역할 경계입니다. 입력·출력이 독립적이고(Port/DTO 계약으로 넘김) 전문성이 다른 곳(도메인 로직 / SQL·마이그레이션 / HTTP·OpenAPI / React)에서만 나눕니다.
  • domain과 application은 한 Agent(core-engineer)가 맡습니다. 유스케이스는 도메인 모델을 계속 이어서 해석해야 하므로 나누면 맥락이 끊깁니다.
  • 구현자는 자기 결과를 합격 처리하지 않습니다. 판정은 quality-gate(결정적)와 리뷰 Agent(판단형)가 하고, 둘 다 코드를 수정하지 않습니다(Edit 없음, 자기 판정 파일만 Write).
  • 각 Agent의 tools는 최소 권한이며, 파일 산출물을 쓰는 Agent는 Write 권한을 갖습니다(없으면 저장에 실패하거나 본문 요약으로 때우는 실패가 납니다).

6.5 Agent 파일 예시: core-engineer (구성 단계에서 이 형식으로 생성)

---
name: core-engineer
description: 계획(artifacts/01-plan.md)에 따라 domain과 application 계층(엔티티, 값 객체, 도메인 서비스, 유스케이스, Port)을 구현할 때 사용한다. infra, web, 테스트 코드는 수정하지 않는다.
tools: Read, Grep, Glob, Write, Edit, Bash
model: sonnet
---

당신은 이 프로젝트의 domain/application 계층 담당 엔지니어입니다.

## 책임
- backend/src/app/domain/** 과 backend/src/app/application/** 만 수정한다.
- 규칙은 엔티티·값 객체에 두고, 유스케이스는 Port를 호출해 조율만 한다.
- 외부 통신은 application/ports 에 Protocol로 정의하고 구현은 infra 담당에게 맡긴다.

## 입력
- artifacts/00-input.md, artifacts/01-plan.md, artifacts/02-tests.md(실패하는 테스트 목록)

## 출력
- 코드 변경 + artifacts/20-agent-outputs/core.md (변경 파일, 결정 사유, 남은 위험)
- 저장 실패 시 재시도하고, 그래도 안 되면 TaskUpdate로 차단을 보고한다(본문 요약으로 대체 금지).

## 작업 방식
1. layer-architecture-rules 스킬로 경계 규칙을 확인한다.
2. 실패하는 테스트를 통과시키는 최소 구현을 한다(테스트 수정 금지).
3. 파일이 300줄에 가까워지면 책임별로 분리한다.
4. 변경 후 uv run pytest tests/unit, ruff, mypy, lint-imports 를 실행한다.

## 팀 통신
- 수신: orchestrator의 Task, test-engineer의 계약 변경 알림
- 발신: Port 시그니처 변경이 필요하면 feature-planner·infra-engineer에게 '충돌' 메시지, 완료 시 orchestrator에게 '완료'
- 차단: 요구사항이 모호해 추측이 필요하면 멈추고 질문 목록을 남긴다

## 하지 말아야 할 일
- infra/web/tests/frontend 파일 수정, pyproject·uv.lock 수정, uv add 실행
- domain·application에서 fastapi, sqlalchemy, httpx, redis, app.config import
- 테스트를 약하게 고쳐 통과시키기

6.6 모델 정책 (역할별, 일괄 지정 금지)

  • opus: 구조 판단·상충 해소(feature-planner, review-architecture, review-lead). sonnet: 구현과 의미 해석(엔지니어, 정확성·보안 리뷰, release-checker). haiku: 규칙 기반 점검(quality-gate, review-conventions).
  • sonnet이 부족해 보이면 바로 opus로 올리기 전에 같은 모델의 높은 effort를 먼저 시험합니다.
  • Agent Team에서는 frontmatter의 model이 실제 실행 모델을 보장하지 못할 수 있으므로, Orchestrator의 팀 생성 지시와 벤치마크 기록에 같은 모델 정책을 명시합니다.
  • 배정한 티어로 실제 확인합니다: haiku 역할의 지침이 충분히 구체적인지, opus 역할이 과설명으로 토큰을 낭비하지 않는지.

10.3 hooks와 권한 (.claude/settings.json)

Skill 지침은 AI가 "기억해서" 지키는 규칙이고, hooks와 권한은 하네스가 강제하는 규칙입니다. 반드시 지켜야 하는 것은 hooks/권한으로 겁니다.

장치시점동작
포맷·린트·파일 길이 hook (구현됨).py 편집 직후 (PostToolUse).claude/hooks/post_edit.py: ruff format + ruff check --fix 적용, 못 고친 오류와 파일 길이 초과를 Claude에게 즉시 알림(결정적, 토큰 비용 없음)
가드 hook (구현됨)도구 호출 직전 (PreToolUse).claude/hooks/guard.py: .env* 읽기·쓰기와 uv.lock 직접 편집, pip install/venv는 차단. APP_PROFILE=product 대상 alembic 명령은 차단, alembic downgrade|stamp와 .env가 들어간 Bash 명령은 사람 확인(local·dev의 alembic upgrade는 자동 허용)
보호 파일 수정 확인 (구현됨: 권한 규칙)편집 직전pyproject.toml, mise.toml, Jenkinsfile, infra/server/** 수정은 매번 묻고(ask), .env*·uv.lock 편집은 거부(deny)
종료 전 게이트 (선택, 미구현)작업 종료 시변경이 있으면 run_gates.py 실행, 실패하면 완료 보고 대신 수정 계속. 필요성이 확인되면 Stop 훅으로 추가
권한 허용상시uv run pytest/ruff/mypy/lint-imports, python scripts/*, pnpm lint/test/typecheck, 읽기용 git status/diff/log
권한 차단 (구현됨)상시.env* 읽기, git push, git reset --hard 등 되돌리기 어려운 명령, product 대상 alembic 명령(가드 hook이 거부), rm -rf

구성 단계에서 확인한 것: hooks는 {"hooks": {"이벤트": [{"matcher": "...", "hooks": [{"type": "command", "command": "..."}]}]}} 형식이고, 입력은 stdin JSON(tool_name, tool_input.file_path 등)입니다. 차단·확인은 PreToolUse의 hookSpecificOutput.permissionDecision(deny/ask)으로, 편집 후 알림은 PostToolUse의 additionalContext로 전달합니다(Claude Code 설정 스키마 기준). 권한 경로 규칙은 Read(경로)/Edit(경로) 형식입니다. 구성 후 실제로 확인했습니다: .env 읽기는 권한 규칙이 거부했고, pip install은 가드 hook이 차단했으며, 편집 후 hook이 임시 파일의 포맷을 고치고 오류를 알려 줬습니다. 확인은 macOS에서만 했으므로 Windows 팀원은 14.2절의 점검을 해 주세요.

10.4 사람 승인 게이트

승인은 산출물에 라벨을 붙이는 것이 아니라 흐름을 멈추고 묻는 행동입니다. 아래 지점에 도달하면 Orchestrator는 산출물 저장, 개선 기록, 팀 정리까지 마친 뒤 승인 요청을 하고 멈춥니다. 명시적 승인 전에는 해당 행동을 하지 않고, 승인 상태를 사용 가능으로 바꾸지 않습니다.

승인 지점이유승인 시 일어나는 일
git commit / push / PR 생성 / 머지이력·원격에 반영(되돌리기 어려움)사용자가 요청한 때에만 커밋. push·머지는 사람이 수행
의존성 추가·변경 (uv add, pnpm add)공급망 위험(인터넷에서 직접 설치), 라이선스, 크기승인된 패키지만 추가하고 uv.lock 갱신 diff를 보고
DB 마이그레이션 실행 (product)운영 데이터 비가역 변경local·dev는 자동(dev는 main 머지 시 배포 파이프라인의 deploy.sh dev가 적용, 승인 없음). product만 dev 검증 후 Jenkins 승인을 거쳐 deploy.sh product가 적용. AI는 product에서 실행하지 않고, downgrade/stamp는 모든 환경에서 사람 확인
비밀·.env·프로파일 값 변경보안, 서버 간 불일치AI는 변경이 필요한 키 이름과 절차만 안내. 값 입력은 사람
공개 API 호환 깨짐 (필드 삭제·타입 변경)프론트·외부 소비자 영향버전 전략(/api/v2) 또는 단계적 변경 합의
배포 (dev 자동 외 product)운영 영향Jenkins input 게이트에서 release-managers가 승인. AI는 배포하지 않음
대형 변경 계획 (새 Aggregate·마이그레이션·계층 구조 변경)되돌리는 비용이 큼계획 승인 후 구현 착수
## 승인 요청

- 승인 대상: {예: users 테이블에 email_verified 컬럼 추가 마이그레이션을 product DB에 실행}
- 필요한 이유: {비가역 스키마 변경, 운영 영향 가능}
- 승인하면 일어나는 일: {실행할 행동}
- 지금 상태: 사람 승인 필요 (아직 실행하지 않음)
- 확인해 주세요: {expand/contract 호환성, 롤백 방법 등 핵심 항목}
- 보류하면: {대안 또는 다음 행동}
