1. 목표와 원칙

미리 만든 고정 리포트 몇 개를 보는 대신, 사용자가 그때그때 필요한 리포트를 직접 설계하고 결과가 마음에 들면 이름을 붙여 저장합니다. 저장한 리포트는 열 때마다 최신 데이터로 다시 조회됩니다. 결과 표로 엑셀처럼 차트를 만들고, 제목·범례·가로축·세로축을 설정합니다.

  • 데이터는 두 가지: Deal과 Deal Actions. 두 엔티티의 컬럼을 섞어 고를 수 있습니다.
  • 리포트 = 컬럼 + 조건 + (자동 생성) SQL + 차트 설정. SQL을 직접 작성하거나 고치는 기능은 없습니다(확정). 화면에서 고르면 서버가 SQL을 만듭니다. 만든 SQL은 "생성 SQL 보기"로 읽기 전용으로 보여 주고 리포트와 함께 저장합니다(11장 Q1).
  • 조회 먼저, 저장은 나중: 디자이너에서 "조회"로 결과를 확인하고, 결과가 있을 때만 "저장" 버튼이 켜집니다.
  • 행 단위를 항상 보여 줌: Action 컬럼이나 조건이 들어가면 결과가 "Action 1건 = 1행"이 되어 Deal 금액 합계가 부풀 수 있습니다. 화면 위쪽 데이터 범위 표시로 지금 행이 무엇인지 늘 알려 주고, 위험한 조합에는 경고를 띄웁니다(7.3).
  • 금액은 다른 화면처럼 기본 천원 표시, 날짜·시각은 서버 시간대 기준입니다.

      6. 컬럼 포맷·그룹핑·집계
      

      6.1 포맷(데이터 표현 방법)
      

      
  
      형식포맷 선택지(기본은 굵게)
      
  
      텍스트·코드·사용자그대로 · 앞 N자만 · (코드) 이름 / key
      
  
      숫자천 단위 구분(1,234) · 천원 · 백만원 · 소수 1자리 · 백분율(구성비)
      
  
      날짜·시각YYYY-MM-DD · YYYY-MM-DD HH:mm · 연도(2026) · 분기(2026 Q4) · 월(2026-10) · 요일 · 상대("3일 전")
      

      

      날짜를 연도·분기·월로 포맷하면 그 단위로 묶입니다(그룹핑을 켰을 때). 금액 컬럼은 기본 "천원"입니다.
      


      6.2 그룹핑과 집계 규칙
      

        
  
      • 컬럼 설정의 "그룹핑"을 켜면 그 컬럼 값이 같은 행끼리 묶입니다. 여러 컬럼을 켜면 그 조합으로 묶습니다(예: Vendor × 분기).
        • 
  
      • 그룹핑된 컬럼이 하나라도 있으면, 그룹핑하지 않은 나머지 컬럼은 반드시 집계로 바뀝니다.
    
          
      
        • 숫자 컬럼: 합계(sum) · 평균(avg) · 최소(min) · 최대(max) 중 하나를 고릅니다. 기본은 합계(Status 체류 일수는 평균).
          • 
      
        • 숫자가 아닌 컬럼: 건수(count) 또는 고유 건수(count distinct)만 고를 수 있습니다(11장 Q3). 고르지 않으면 "그룹핑하거나 빼세요" 안내와 함께 조회가 막힙니다.
          • 
    
        
  
        • 
  
      • 그룹핑이 없으면 집계 없이 행 그대로 나옵니다.
        • 
  
      • 결과 표 맨 아래에 합계 행(숫자 집계 컬럼만)을 켤 수 있습니다.
        • 

      

      칩에는 상태가 짧게 붙습니다: 그룹 그룹핑, 합계/평균… 집계, 아무것도 없으면 행 값 그대로.
      


      7. 조건과 Join 규칙
      

      7.1 조건 빌더
      

      조건 한 줄 = 필드 · 연산자 · 값. 필드는 Deal과 Deal Actions 모두에서 고릅니다. 연산자는 형식에 따라 달라집니다.
      

      
  
      형식연산자값 입력
      
  
      텍스트포함 · 같음 · 시작 · 비어 있음 · 비어 있지 않음글자
      
  
      코드·사용자다음 중 하나 · 다음이 아님 · 비어 있음목록 다중 선택(Forecast 다중 선택과 같은 체크 목록)
      
  
      숫자= · ≠ · > · ≥ · < · ≤ · 범위숫자(금액은 천원 입력)
      
  
      날짜·시각범위 · 이전 · 이후 · 상대 기간(올해 · 이번 분기 · 이번 달 · 최근 N일 · 오늘 이전)날짜 또는 기간 선택
      

      

      상대 기간은 저장된 리포트를 열 때마다 서버 날짜 기준으로 다시 계산됩니다(예: "올해"로 저장하면 내년엔 내년이 됨).
      

      조건 결합(확정): 리포트 하나의 조건은 모두 AND("모든 조건을 만족") 또는 모두 OR("하나라도 만족") 중 하나입니다. 조건 카드 위의 선택 하나로 정하며, AND와 OR를 섞거나 괄호로 묶을 수는 없습니다. 섞인 조합·묶음 깊이는 이후 기능 개선으로 미룹니다.
      


      7.2 Join 규칙
      

      
  
      컬럼·조건에 쓰인 엔티티데이터 범위(행 1개)SQL
      
  
      Deal만Deal 1건FROM deals
      
  
      Actions가 컬럼에 있음Action 1건(Deal 정보는 각 행에 반복)deals JOIN deal_actions — Action이 없는 Deal은 빠짐
      
  
      Actions가 조건에만 있음Deal 1건("조건에 맞는 Action이 하나라도 있는 Deal")EXISTS (SELECT … FROM deal_actions …)
      

      

      요청하신 "두 엔티티가 모두 있으면 Join"을 따르되, Action이 조건에만 쓰일 때는 행이 불어나지 않도록 EXISTS로 거르는 것을 제안합니다(11장 Q2). 이렇게 하면 "이번 달 고객 미팅을 한 Deal의 금액 합계"가 정확히 나옵니다.
      


      7.3 데이터 범위 표시와 경고
      

        
  
      • 디자이너 맨 위에 "행 단위: Deal 1건"(파랑) 또는 "행 단위: Action 1건 · Deal과 Join"(보라)을 항상 보입니다.
        • 
  
      • Deal 숫자는 Deal마다 한 번만 집계(확정, Q5=B): 행 단위가 Action이어도 Deal 숫자 컬럼(금액·Users·Status 체류 일수)의 합계·평균은 Deal당 한 번만 셉니다. 예: 금액 1억인 Deal에 Action이 3건이면 3행으로 나와도 금액 합계는 1억입니다. 최소·최대는 원래 중복의 영향이 없습니다. 이때 범위 표시에 "Deal 숫자는 Deal마다 한 번만 더합니다"를 함께 보입니다.
        • 

      


      8. 저장
      

      조회 결과가 나온 뒤에만 "저장"이 켜집니다. 누르면 아래 대화상자가 열립니다.
      

      
  
      
    
      
      
      리포트 저장
      
      
      
      
      
      저장 내용: 컬럼·조건·정렬·행 수·차트 설정과 생성 SQL. 결과 데이터는 저장하지 않고 열 때마다 다시 조회합니다.
      
      
      
    
      
  
      

      

        
  
      • 이름은 필수, 100자 이내, 같은 사람의 리포트 안에서 중복 불가. 설명은 선택(1,000자).
        • 
  
      • 편집 중인 저장 리포트는 "저장"(덮어쓰기)과 "다른 이름으로 저장"을 함께 보입니다.
        • 
  
      • 저장하지 않고 화면을 떠나면 "저장하지 않은 변경이 있습니다" 확인을 띄웁니다.
        • 

      


      9. 차트
      

      결과 표의 열을 엑셀처럼 가로축(범주)과 값(계열)으로 골라 차트를 만듭니다. 결과 카드의 "차트" 탭에서 엽니다. 차트 설정은 리포트와 함께 저장됩니다(차트 없이 저장도 가능). 구현은 이미 쓰고 있는 Chart.js를 씁니다.

      차트 종류를 바꾸면 미리보기가 바로 바뀝니다(목업은 일부 종류만 그림).
      

      
  
      종류쓰임
      
  
      세로 막대 · 가로 막대 · 누적 막대 · 100% 누적범주별 비교, 구성(예: Vendor × 분기)
      
  
      꺾은선 · 영역시간 추이(월·분기)
      
  
      원 · 도넛구성비(계열 1개만)
      
  
      분산형숫자 두 개의 관계(예: 금액 × 체류 일수)
      
  
      콤보(막대 + 선)금액(막대)과 건수(선, 보조 축)를 함께
      

      

        
  
      • 범주 열은 그룹핑한 컬럼, 값 열은 숫자(집계) 컬럼만 고를 수 있습니다. 그룹핑이 없는 결과는 "그룹핑한 결과로 차트를 만들 수 있습니다"를 안내합니다.
        • 
  
      • 그룹핑 컬럼이 두 개면(예: Vendor·분기) 두 번째를 계열로 써서 누적 막대를 만듭니다. "행/열 전환"은 범주와 계열을 바꿉니다.
        • 
  
      • 결과 표·차트에서 Deals 목록으로 이동하는 Drill-down은 두지 않습니다(확정).
        • 

      


      10. 권한·보안·한도
      

      
  
      항목제안
      
  
      만들기·저장admin·sales. user(조회자)는 공개 리포트 보기만
      
  
      수정·삭제만든 사람과 admin
      
  
      데이터 범위모든 역할이 모든 Deal을 보는 지금 규칙과 같음(Deals 목록과 동일)
      
  
      SQLSQL 입력란 없음. 사용자는 SQL을 직접 작성·수정할 수 없음(Q1 확정). 서버가 허용 필드·연산자 목록과 파라미터 바인딩으로만 SQL을 만들고, 읽기 전용 트랜잭션·문장 시간 제한(예: 10초)으로 실행
      
  
      한도컬럼 30개, 조건 20개, 미리보기 최대 10,000행, 저장 리포트 수 제한 없음
      
  
      저장 형식리포트 정의는 JSON(컬럼·조건·정렬·차트). 생성 SQL은 표시·감사용으로 함께 저장하되, 실행은 항상 최신 정의로 다시 생성
      

      


      11. 결정 사항
      

      2026-10-26 사용자 답변 반영(전부 확정).
      

      
  
      번호주제결정
      
  
      Q1SQL 직접 작성확정: SQL 직접 작성·수정 불가(입력란 없음). 화면 선택으로 서버가 만든 SQL만 읽기 전용으로 보여 주고 함께 저장
      
  
      Q2Action이 조건에만 있을 때확정: EXISTS(Deal 단위 유지). Action이 컬럼에 있을 때만 Join
      
  
      Q3그룹핑 시 숫자가 아닌 컬럼확정: 건수·고유 건수만, 아니면 그룹핑하거나 빼도록 안내
      
  
      Q4조건 결합확정: 리포트 단위로 전부 AND 또는 전부 OR. 섞기·묶음은 이후 개선
      
  
      Q5Action 단위 행에서 Deal 금액 합계확정(B): Deal 숫자의 합계·평균은 Deal마다 한 번만(예: 1억 Deal에 Action 3건 → 1억)
      
  
      Q6공개 범위확정: "모든 사용자" / "나만 보기"
      
  
      Q7Drill-down확정: 없음
      
  
      Q8엑셀 내보내기확정: 이후 단계(이번 범위 밖)
      
  
      Q9Deal History 데이터확정: 이번에는 Deal·Deal Actions만
      

      


      구현은 12장의 5단계로 나눠 진행합니다.
      


      12. 구현 단계
      

      단계마다 계획 → 테스트 먼저 → 구현(domain·application → infra → web → frontend) → 게이트 → 리뷰 → 커밋을 한 번씩 돕니다. 각 단계가 끝나면 그 단계만으로 동작을 확인할 수 있게 나눴고, 뒤 단계는 앞 단계 결과 위에만 쌓입니다. 가장 위험한 부분(SQL 생성·보안·집계 정확성)을 1단계에 몰아 먼저 검증합니다.
      


      
  1. 조회 엔진(API)→
  2. 디자이너 화면(조회만)→
  3. 저장·목록·열기→
  4. 차트→
  5. 문서·마무리

      


      1단계. 필드 카탈로그와 조회 엔진 (백엔드)
      

      
  
      항목내용
      
  
      목표리포트 정의(JSON)를 받아 안전한 SQL을 만들고 실행해 결과 행을 돌려준다. 화면 없이 API로 검증
      
  
      domainReportDefinition(컬럼·조건·결합 AND/OR·정렬·행 수) 값 객체와 검증 규칙: 허용 필드만, 컬럼 1~30개·조건 0~20개, 형식별 포맷·연산자·집계 조합(6·7장), 그룹핑이 있으면 나머지 컬럼은 집계 필수(숫자: 합계·평균·최소·최대, 그 밖: 건수·고유 건수), 행 수 100·1,000·10,000
      
  
      application필드 카탈로그 조회, 리포트 실행 유스케이스. Port ReportQueryRunner(정의 → 행·생성 SQL 문자열). 상대 기간(올해·이번 분기·최근 N일)은 서버 날짜로 풀어서 넘김
      
  
      infraSQLAlchemy Core로 SQL 생성: 허용 필드 → 컬럼 식 매핑, 이름 표시용 조인은 필요한 것만, Action이 컬럼에 있으면 JOIN · 조건에만 있으면 EXISTS(Q2), Deal 숫자의 합계·평균은 Deal마다 한 번(Q5=B: deal_id별 1행 하위 쿼리), 날짜 묶음(연·분기·월), 값은 모두 파라미터 바인딩, 읽기 전용 트랜잭션 + 문장 시간 제한(예: 10초). 표시용 SQL 문자열도 함께 생성
      
  
      webGET /api/v1/reports/fields(필드·형식·포맷·연산자·집계 목록), POST /api/v1/reports/query(정의 실행, 저장 안 함, 응답: 열 정의·행·총 행 수·생성 SQL·실행 시간). 로그인한 모든 역할 조회 가능. 잘못된 정의는 422(어느 컬럼·조건이 왜 틀렸는지)
      
  
      마이그레이션없음
      
  
      테스트정의 검증 단위 테스트, SQL 생성 단위 테스트(형태·파라미터), 실제 DB 계약 테스트(JOIN/EXISTS 결과 행 수, Deal당 1번 합계가 Deals 목록 원장과 같은지, 날짜 묶음 경계, 시간 제한), functional 시나리오(수집만)
      
  
      완료 기준API로 "Vendor × 분기별 금액 합계(Lost 제외, 올해)"를 조회해 Deals 목록에서 같은 조건으로 센 건수·금액과 같다. 허용 밖 필드·연산자는 422
      

      


      2단계. 리포트 디자이너 화면 (조회만)
      

      
  
      항목내용
      
  
      목표4장 디자이너로 컬럼·조건을 골라 조회하고 결과 표를 본다. 저장은 아직 없음
      
  
      frontendReports 메뉴의 "준비 중"을 목록 자리(빈 목록 + "+ 새 리포트")로 교체, /reports/new 디자이너: 필드 목록(검색, Deal/Actions 구분 색), 컬럼 칩(추가·삭제·끌어서 순서, 같은 필드 여러 번), 컬럼 설정(표시 이름·포맷·그룹핑·집계), 조건 빌더(필드·연산자·값, 코드 다중 선택, 상대 기간), 조건 결합 AND/OR 선택 하나(Q4), 정렬·최대 행, 데이터 범위 표시(행 단위·EXISTS·Deal당 1번 안내), "조회", 결과 표(숫자 오른쪽 정렬, 금액 천원, 합계 행 선택), 생성 SQL 보기(읽기 전용), 오류는 해당 칩·조건 옆에 표시
      
  
      backend없음(1단계 API 사용, pnpm gen:api)
      
  
      테스트Vitest 화면 테스트: 칩 추가·순서·설정, 그룹핑 켜면 집계 선택 활성, 숫자 아님 집계 제한, Action 컬럼 추가 시 범위 표시 변화, AND/OR 전환, 조회 결과·오류 표시. 설계는 저장 전까지 화면 상태(떠날 때 확인)
      
  
      완료 기준시안 4장 목업의 동작이 실제 데이터로 된다
      

      


      3단계. 저장·목록·열기·편집
      

      
  
      항목내용
      
  
      목표결과가 나온 리포트를 이름·설명과 함께 저장하고, 목록에서 열어 최신 데이터로 다시 본다
      
  
      마이그레이션reports 테이블 1개(순수 추가): id(BIGINT identity), name, description, visibility(public/private), owner_id(users FK RESTRICT), definition(JSONB), generated_sql(TEXT, 표시·감사용), chart(JSONB, 4단계에서 사용, NULL 허용), created_at, updated_at. 같은 owner 안에서 이름 유일(대소문자 무시)
      
  
      domain·applicationReport 엔티티, 만들기·수정(덮어쓰기)·다른 이름으로 저장·복제·삭제·목록·보기 유스케이스, Port ReportRepository. 권한: 만들기·저장은 admin·sales, 수정·삭제는 만든 사람·admin, 보기는 공개 리포트 또는 내 리포트(Q6). 열 때는 저장된 정의로 SQL을 다시 생성해 실행(생성 SQL 열은 표시용)
      
  
      webGET/POST /api/v1/reports, GET/PUT/DELETE /api/v1/reports/{id}, POST /api/v1/reports/{id}/run(또는 보기 응답에 결과 포함 — 계획에서 결정), 이름 중복 409
      
  
      frontendReports 목록(검색, 전체/내가 만든, 데이터 태그, ⋯ 메뉴: 열기·편집·복제·삭제), 저장 대화상자(이름 필수·설명·공개 범위), /reports/{id} 보기, /reports/{id}/edit 편집("저장"/"다른 이름으로 저장"), 저장 안 된 변경 표시와 떠날 때 확인
      
  
      테스트권한별(admin·sales·user) 저장·수정·삭제·보기, 비공개 리포트 숨김, 이름 중복, Repository 계약, 저장 후 다시 열면 같은 결과, functional(수집만)
      
  
      완료 기준저장 → 목록 → 다시 열기 → 편집 → 다른 이름으로 저장이 끝까지 된다. 퇴사한 만든 사람의 리포트도 "이름(퇴사)"로 남는다
      

      


      4단계. 차트
      

      
  
      항목내용
      
  
      목표결과 표로 엑셀처럼 차트를 만들고 리포트와 함께 저장한다(9장)
      
  
      domain·web차트 설정 값 객체와 검증(종류, 범주 열은 그룹핑 컬럼, 값 열은 숫자 집계 컬럼, 원·도넛은 계열 1개), 리포트 저장·수정 요청에 chart 추가(NULL이면 차트 없음). 마이그레이션 없음(3단계 열 사용)
      
  
      frontend결과 카드의 "차트" 탭: 종류(세로·가로 막대, 누적, 100% 누적, 꺾은선, 영역, 원, 도넛, 분산형, 콤보), 가로축(범주)·값(계열) 선택, 행/열 전환, 제목, 범례 위치, 데이터 레이블, 축 제목, 세로축 최소·최대, 콤보 보조 축. 기존 Chart.js·react-chartjs-2 사용(새 의존성 없음, 필요한 요소만 등록), 그룹핑 없는 결과는 안내
      
  
      테스트설정 검증 단위 테스트, 화면 테스트(종류·설정 변경이 차트 옵션에 반영, 저장 후 다시 열면 같은 설정). 차트 그리기 자체는 기존처럼 react-chartjs-2 mock
      
  
      완료 기준시안 9장 목업의 설정이 모두 동작하고 저장·다시 열기에서 유지된다
      

      


      5단계. 문서·마무리
      

      
  
      항목내용
      
  
      문서docs/user-guide.html에 Reports 장 신설(만들기·조건·그룹핑·저장·차트·권한, Deal당 1번 합계 설명), docs/prd.html 7.4·P7 상태, docs/dev-guide.html(SQL 생성 원칙·허용 필드 추가 방법), docs/source-guide.md, CLAUDE.md 변경 이력. 이 시안 문서는 확정본으로 옮긴 뒤 정리
      
  
      점검큰 데이터에서 조회 시간(시간 제한·인덱스 필요 여부), 한도값(행 10,000·컬럼 30·조건 20) 재확인, 브라우저 수동 확인(키보드·화면낭독기·좁은 화면)
      

      

      문서 갱신은 단계마다 그 단계 기능만큼 함께 하고, 5단계에서 전체를 한 번 정리합니다.
