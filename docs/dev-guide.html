이 문서는 코드 스타일, 객체지향 설계(SOLID), 아키텍처, 디자인 패턴, 개발 환경, 빌드, 테스트, CI/CD의 기본 방침을 정의합니다. 도구 버전은 시점에 따라 바뀌므로, 실제 도입 시점에 각 공식 문서로 최신 버전과 옵션을 확인하세요.

Jenkins, uv, FastAPI, Ruff 관련 내용은 Context7으로 조회한 공식 문서를 기준으로 작성했습니다.

1. 개요 및 원칙

타입 우선

모든 공개 함수·메서드에 타입 힌트를 붙이고 mypy(또는 pyright) strict로 검증합니다.

도메인 중심

비즈니스 규칙은 프레임워크(FastAPI, SQLAlchemy)와 분리된 순수 파이썬 객체에 둡니다.

의존성 역전

상위 정책이 인터페이스(Protocol/ABC)를 소유하고, DB·외부 API 같은 세부사항이 이를 구현합니다.

자동화

포맷·린트·타입·테스트는 사람이 아닌 pre-commit과 CI가 강제합니다.

계약 기반

OpenAPI 스키마를 단일 진실 공급원으로 삼아 프론트 타입을 자동 생성합니다.

재현 가능성

lock 파일(uv.lock, pnpm-lock.yaml), mise로 고정한 도구 버전(Python, Node, uv, pnpm), 동일 명령(just)으로 로컬·CI·운영 환경을 일치시킵니다.

"최대한 객체지향"에 대한 주의. 파이썬은 멀티 패러다임 언어입니다. 상태와 행동이 함께 있는 도메인 개념(엔티티, 값 객체, 서비스, 정책)은 클래스로 모델링하되, 상태 없는 변환·유틸 로직까지 억지로 클래스로 감싸지 마세요(모듈 수준 순수 함수가 더 파이썬답습니다). 목표는 "클래스 개수"가 아니라 응집도 높고 결합도 낮은 객체 협력입니다.

3.2-1 기존 venv에서 uv로 전환 (이 프로젝트에 적용한 절차)

# 1) 기존 venv 제거 (패키지가 pip뿐이라 보존할 내용 없음)
rm -rf .venv

# 2) backend에 uv 프로젝트 생성 (src 레이아웃, uv_build 백엔드)
uv init backend --lib --name neoine-sales-backend --python 3.14 --vcs none --no-readme
cd backend
mv src/neoine_sales_backend src/app        # import 이름을 app으로 (pyproject에 module-name = "app" 추가)

# 3) 의존성 추가 -> pyproject.toml + uv.lock 갱신, backend/.venv 자동 생성
uv add "fastapi[standard]" "uvicorn[standard]" pydantic pydantic-settings \
       "sqlalchemy[asyncio]" asyncpg alembic structlog
uv add --dev pytest pytest-asyncio pytest-cov httpx factory-boy \
       ruff mypy import-linter pre-commit

# 4) 검증
uv sync --locked && uv run ruff check . && uv run mypy src && uv run lint-imports
  • 이후 규칙: pip install, python -m venv, requirements.txt를 쓰지 않습니다. 의존성은 uv add/uv remove, 실행은 uv run, 동기화는 uv sync로 통일하고 pyproject.toml과 uv.lock을 함께 커밋합니다. .venv는 커밋하지 않습니다(.gitignore).
  • PyCharm: Settings → Project → Python Interpreter에서 backend/.venv/bin/python(uv 환경)을 지정하고, backend/src를 Sources Root로 표시하며 backend/tests를 Test Sources Root로 표시합니다. 기존 SDK Python 3.14 (neoine-sales)는 삭제된 루트 .venv를 가리키므로 교체해야 합니다.
  • VS Code: python.defaultInterpreterPath를 backend/.venv/bin/python으로 지정합니다.

3.5.2 설계 원칙

  • 빌드는 한 번, 릴리스 번들은 하나: 같은 릴리스 번들(git SHA 버전)을 dev에서 검증한 뒤 그대로 product에 배포합니다. 프로파일은 런타임 설정 APP_PROFILE(환경변수 또는 서버 .env)으로만 결정하고, 프로파일별로 번들을 따로 빌드하지 않습니다.
  • 네임스페이스: 백엔드 변수는 모두 APP_ 접두어(pydantic-settings의 env_prefix). 다른 시스템 변수와 충돌하지 않습니다.
  • "기본값의 차이"는 코드, "환경마다 다른 값"은 환경변수: 디버그 여부·로그 형식·API 문서 노출 같은 프로파일별 기본 동작은 LocalSettings/DevSettings/ProductSettings 클래스로 표현합니다(OCP: 프로파일 추가 시 클래스만 추가). DB 주소·비밀키·외부 URL 같은 값은 환경변수로 주입합니다.
  • 비밀은 환경변수로만: 코드·Git·릴리스 번들·Jenkinsfile·로그에 넣지 않습니다. SecretStr으로 선언해 로그/repr에서 마스킹합니다.
  • 프로파일 간 비밀 재사용 금지: dev와 product의 DB 비밀번호, JWT 키, API 키는 서로 달라야 합니다. dev 유출이 product 침해로 이어지면 안 됩니다.
  • 시작 시 즉시 검증(fail-fast): 필수 변수 누락·타입 오류는 애플리케이션 기동 단계에서 실패시킵니다. product는 추가로 안전 조건(디버그 꺼짐, HTTPS 쿠키, CORS 와일드카드 금지 등)을 검증합니다.
  • 계층 규칙: Settings는 app.config에 두고 domain/application은 import하지 않습니다. container.py(Composition Root)와 web의 앱 팩토리에서만 읽고, 필요한 값만 생성자로 주입합니다.

3.5.5 설정 코드 구조 (backend/src/app/config/)

파일 300줄 제한(5.2절)에 따라 base.py(공통 필드) · profiles.py(프로파일별 클래스) · __init__.py(로더)로 나눕니다. 아래 코드는 pydantic-settings 공식 문서(env_prefix, env_file, SecretStr, 검증기)를 확인하고, 세 프로파일과 product 검증 실패 시나리오를 직접 실행해 동작을 확인했습니다. 실제 구현은 backend/src/app/config/, 테스트는 backend/tests/unit/test_settings.py(12개)에 있으며, 아래 코드는 지면상 발췌본이라 세부(타입 별칭, 일부 필드)가 실제 파일과 조금 다를 수 있습니다. 기준은 실제 소스입니다.

# config/base.py
class Profile(StrEnum):
    LOCAL = "local"
    DEV = "dev"
    PRODUCT = "product"


class Settings(BaseSettings):
    """모든 프로파일 공통 필드. 값은 APP_ 접두어 환경변수에서 읽는다."""

    model_config = SettingsConfigDict(
        env_prefix="APP_", env_file=".env", env_file_encoding="utf-8", extra="ignore"
    )

    profile: Profile
    debug: bool = False
    enable_docs: bool = False
    log_level: Literal["DEBUG", "INFO", "WARNING", "ERROR"] = "INFO"
    log_format: Literal["console", "json"] = "json"
    workers: int = Field(default=2, ge=1)

    cors_allowed_origins: list[str] = Field(default_factory=list)   # 환경변수는 JSON 배열 문자열
    cookie_secure: bool = True
    jwt_secret: SecretStr                                           # 비밀: 기본값 없음 = 필수
    access_token_ttl_minutes: int = 15

    database_url: PostgresDsn                                       # 필수 (비밀 포함 URL)
    db_pool_size: int = Field(default=10, ge=1)
    db_echo: bool = False
    redis_url: RedisDsn | None = None   # 현재 미사용. 큐·캐시를 도입할 때 필수로 바꾼다
    sentry_dsn: SecretStr | None = None


# config/profiles.py  - 프로파일별 "기본 동작"의 차이만 표현
class LocalSettings(Settings):
    profile: Profile = Profile.LOCAL
    debug: bool = True
    enable_docs: bool = True
    log_level: Literal["DEBUG", "INFO", "WARNING", "ERROR"] = "DEBUG"
    log_format: Literal["console", "json"] = "console"
    cookie_secure: bool = False        # 로컬은 http
    db_echo: bool = True
    workers: int = 1


class DevSettings(Settings):
    profile: Profile = Profile.DEV
    enable_docs: bool = True
    log_level: Literal["DEBUG", "INFO", "WARNING", "ERROR"] = "DEBUG"


class ProductSettings(Settings):
    profile: Profile = Profile.PRODUCT
    workers: int = 4

    @model_validator(mode="after")
    def _check_safe_for_product(self) -> Self:
        problems: list[str] = []
        if self.debug or self.enable_docs or self.db_echo:
            problems.append("debug/enable_docs/db_echo는 product에서 꺼야 합니다")
        if not self.cookie_secure:
            problems.append("cookie_secure는 true여야 합니다")
        if "*" in self.cors_allowed_origins:
            problems.append("CORS에 '*'를 허용할 수 없습니다")
        if len(self.jwt_secret.get_secret_value()) < 32:
            problems.append("jwt_secret은 32자 이상이어야 합니다")
        if self.sentry_dsn is None:
            problems.append("sentry_dsn이 필요합니다")
        if problems:
            raise ValueError("; ".join(problems))
        return self


# config/__init__.py  - 프로파일 선택(새 프로파일 추가 = 클래스 + 이 매핑 한 줄)
_BY_PROFILE: dict[Profile, type[Settings]] = {
    Profile.LOCAL: LocalSettings,
    Profile.DEV: DevSettings,
    Profile.PRODUCT: ProductSettings,
}

class _ProfileSelector(BaseSettings):
    """APP_PROFILE만 먼저 읽는다. 환경변수 또는 .env 파일 어디에 있어도 된다."""
    model_config = SettingsConfigDict(
        env_prefix="APP_", env_file=".env", env_file_encoding="utf-8", extra="ignore"
    )
    profile: Profile = Profile.LOCAL


@lru_cache
def get_settings() -> Settings:
    profile = _ProfileSelector().profile      # 잘못된 값이면 즉시 실패
    return _BY_PROFILE[profile]()
시나리오 (실행 확인)결과

APP_PROFILE=devDevSettings (json 로그, debug=False)
APP_PROFILE=product + APP_DEBUG=true, Sentry 미설정기동 실패: "debug/enable_docs/db_echo는 product에서 꺼야 합니다; sentry_dsn이 필요합니다"
APP_PROFILE=prod (오타)기동 실패: profile 값 검증 오류(local/dev/product만 허용)
.env에만 APP_PROFILE=devDevSettings (환경변수 없이도 인식)
필수 변수(APP_DATABASE_URL, APP_JWT_SECRET 등) 누락기동 실패: Field required
  • list[str] 같은 복합 타입은 환경변수에서 JSON 문자열로 파싱됩니다(예: APP_CORS_ALLOWED_ORIGINS=["https://a.example.com"]).
  • env_file=".env"는 실제 환경변수가 없을 때만 보조로 읽힙니다(환경변수 우선). 서버에서는 systemd 서비스의 WorkingDirectory(/opt/neoine-sales)에 있는 .env를 직접 읽으며, APP_PROFILE도 환경변수 또는 .env 어느 쪽에 있어도 인식합니다.
  • 설정은 get_settings()(lru_cache)로 프로세스당 한 번 로드하고, 테스트에서는 Settings 서브클래스를 직접 생성해 주입합니다.

3.5.7 서버 .env 관리 (dev / product)

  • 원본: 비밀 값은 Git에 두지 않고 사내 비밀번호 관리 도구(또는 HashiCorp Vault)에 보관합니다. 각 서버의 /opt/neoine-sales/.env(소유자 neoine, 권한 600)는 서버 관리자가 neoine 계정으로 직접 편집합니다. 최초 파일은 bootstrap.sh가 APP_PROFILE만 채워 생성합니다(16.6절).
  • 변경 절차: 변경 요청 → (product는 승인자 확인) → 관리자가 모든 해당 서버의 .env를 수정 → 다음 배포 또는 서비스 재시작으로 반영. 변경 이력(누가, 언제, 어떤 키)은 운영 기록에 남기되 값은 기록하지 않습니다.
  • 서버 간 불일치 방지: 수동 관리이므로 서버마다 값이 달라질 위험이 있습니다. deploy.sh가 전환 전에 설정 사전 검증(get_settings() 실행)을 수행해 필수 변수 누락·형식 오류·product 안전 조건 위반을 배포 단계에서 즉시 막습니다(16.4절).
  • 회전: JWT 키·DB 비밀번호·API 키는 정기 회전(예: 분기)하며, 유출 의심 시 즉시 교체합니다. 회전 절차(이중 키 허용 기간 등)는 운영 문서에 별도로 정의합니다.
  • deploy.sh는 .env의 APP_PROFILE이 인자로 받은 환경과 일치하는지 검사해, dev 설정이 product 서버에 올라가는 사고를 막습니다(16.4절).

3.5.8 프론트엔드 환경변수

  • Vite는 VITE_ 접두어 변수만 클라이언트 코드(import.meta.env)에 노출하고, 접두어가 없는 변수(DB_PASSWORD 등)는 undefined입니다(Vite 공식 문서). 단, VITE_ 변수는 빌드 결과물(JS)에 그대로 포함되어 누구나 볼 수 있으므로 비밀을 넣지 않습니다.
  • 값은 빌드 시점에 치환되므로, "빌드 한 번, 릴리스 번들 하나" 원칙을 지키려면 프로파일마다 다른 값이 빌드에 박히지 않도록 설계합니다.

3.5.9 CI(Jenkins)에서의 환경변수

  • CI 테스트는 APP_PROFILE을 지정하지 않고(=local 기본값) 더미 값만 주입합니다. 실제 dev/product 비밀은 CI 빌드에 전달하지 않습니다.
  • 통합 테스트의 DB 주소는 fixture가 만든 임시 DB의 접속 URL을 테스트 코드에서 Settings에 직접 주입합니다(15.6절). 운영·dev 데이터베이스 주소는 CI에 전달하지 않습니다.
  • 릴리스 번들에는 .env와 비밀을 포함하지 않습니다(infra/build_release.sh는 소스·잠금 파일·정적 파일만 복사).

3.5.10 환경변수 체크리스트

  • ☐ 모든 변수가 APP_(백엔드) 또는 VITE_(프론트) 접두어를 사용하고 .env.example과 3.5.3 표에 등록됨
  • ☐ 비밀은 SecretStr + 서버 .env/Vault로만 관리되고 Git·릴리스 번들·로그에 없음
  • ☐ dev와 product의 비밀이 서로 다름
  • ☐ product 기동 검증(디버그·문서·CORS·쿠키·Sentry)을 통과함
  • ☐ VITE_ 변수에 비밀이 없음
  • ☐ 새 변수의 서버 .env 값이 코드 배포보다 먼저 반영됨

"App layer"의 디렉터리 이름은 application입니다(루트 패키지 이름이 이미 app이라 충돌을 피하기 위함). 저장소 루트의 infra/는 배포 자산이고, 백엔드 코드의 app/infra는 Port 구현체 계층입니다.

의존성 방향 규칙: web → application → domain, infra → application → domain. application은 infra를 import하지 않으며, 외부와의 통신은 application/ports의 인터페이스로만 합니다. infra가 그 인터페이스를 구현합니다(의존성 역전). web과 infra는 서로 import하지 않고, 둘을 이어 주는 곳은 Composition Root(container.py)뿐입니다. 이 규칙은 import-linter로 CI(Jenkins)에서 자동 검증합니다.

# pyproject.toml
[tool.importlinter]
root_package = "app"
include_external_packages = true     # 외부 패키지(fastapi, sqlalchemy 등) 금지 규칙에 필요

# 1) 계층 규칙: 위 계층만 아래 계층을 import할 수 있다.
#    같은 줄의 web | infra 는 서로 독립(상호 import 금지)
[[tool.importlinter.contracts]]
name = "계층 의존성: web, infra → application → domain"
type = "layers"
layers = [
    "app.web | app.infra",
    "app.application",
    "app.domain",
]

# 2) domain은 프레임워크·IO 라이브러리를 몰라야 한다
[[tool.importlinter.contracts]]
name = "domain은 순수해야 한다"
type = "forbidden"
source_modules = ["app.domain"]
forbidden_modules = ["fastapi", "pydantic", "sqlalchemy", "httpx", "redis"]

# 3) application은 구체 기술(DB, HTTP, 웹)에 의존하지 않는다 - Port로만 소통

규칙: backend/src와 backend/tests 아래의 Python 소스 파일 하나는 300줄(빈 줄·주석·docstring을 포함한 물리적 총 줄 수)을 넘지 않습니다.

왜 제한하는가. 이 프로젝트의 핵심 목표는 응집도가 높고 결합도가 낮으며, 읽기 쉬운 코드와 단일 책임 원칙(SRP)입니다. 파일이 커진다는 것은 한 모듈이 여러 이유로 변경되고 있다는 가장 눈에 띄는 신호이며, 그 결과 읽는 데 드는 비용이 커지고 변경 충돌과 숨은 결합이 늘어납니다. 줄 수 제한은 이 위험을 기계적으로 조기에 드러내는 안전장치입니다. 300줄은 분리할 시점을 알려 주는 상한이지 채워야 하는 목표가 아닙니다. 대부분의 파일은 100~200줄 안에서 끝나는 것이 이상적입니다.

300줄에 가까워지면: 줄이는 방법이 아니라 책임을 나눈다

줄 수를 맞추려고 코드를 압축하거나 불필요하게 한 줄에 몰아 쓰지 마세요(가독성 저하). 반드시 책임 단위로 분리합니다.

5.3 좋은 예

from dataclasses import dataclass
from decimal import Decimal


@dataclass(frozen=True, slots=True)
class Money:
    """통화 금액 값 객체. 불변이며 같은 통화끼리만 연산할 수 있다."""

    amount: Decimal
    currency: str = "KRW"

    def __post_init__(self) -> None:
        if self.amount < 0:
            raise ValueError("금액은 음수일 수 없습니다")

    def __add__(self, other: "Money") -> "Money":
        if self.currency != other.currency:
            raise ValueError("통화가 다릅니다")
        return Money(self.amount + other.amount, self.currency)

6.2 설계 지침

  • 상속보다 합성: 상속은 "is-a"가 명확하고 리스코프 치환이 성립할 때만. 기본은 협력 객체를 생성자로 주입.
  • 풍부한 도메인 모델: 규칙은 서비스의 if문이 아니라 엔티티 메서드에 둠(빈약한 도메인 모델 지양).
  • 불변식 보장: 객체는 생성 시점부터 항상 유효해야 함(__post_init__ 검증).
  • Tell, Don't Ask: 데이터를 꺼내 판단하지 말고 객체에게 행동을 요청.
  • 생성자 주입: 의존성은 __init__에서 받고, 내부에서 new(직접 생성) 하지 않음. 조립은 Composition Root(container.py)에서만.
  • 전역 상태·싱글턴 모듈 변수 지양, 다중 상속은 Mixin 목적으로 제한.

6.3 엔티티 예시 (풍부한 도메인 모델)

class Order:
    def __init__(self, order_id: OrderId, customer_id: CustomerId) -> None:
        self._id = order_id
        self._customer_id = customer_id
        self._lines: list[OrderLine] = []
        self._status = OrderStatus.DRAFT

    @property
    def total(self) -> Money:
        return sum((l.subtotal for l in self._lines), start=Money(Decimal(0)))

    def add_line(self, product_id: ProductId, qty: int, unit_price: Money) -> None:
        if self._status is not OrderStatus.DRAFT:
            raise OrderNotModifiableError(self._id)
        self._lines.append(OrderLine(product_id, qty, unit_price))

    def confirm(self) -> None:
        if not self._lines:
            raise EmptyOrderError(self._id)
        self._status = OrderStatus.CONFIRMED

    def __eq__(self, other: object) -> bool:
        return isinstance(other, Order) and other._id == self._id

    def __hash__(self) -> int:
        return hash(self._id)

7. SOLID 원칙

S — 단일 책임 원칙 (Single Responsibility)

클래스는 변경 이유가 하나여야 합니다. 주문 도메인 로직, 영속화, 알림 발송은 서로 다른 이유로 바뀌므로 분리합니다.

# ✗ 나쁨: 규칙 + DB + 메일이 한 클래스에
class OrderService:
    def place(self, data):
        ...  # 검증
        self.db.execute("INSERT ...")
        smtplib.SMTP(...).send_message(...)

# ✓ 좋음: 책임 분리
class PlaceOrder:                       # 유스케이스 조율만
    def __init__(self, uow: UnitOfWork, notifier: Notifier) -> None:
        self._uow, self._notifier = uow, notifier

    def execute(self, cmd: PlaceOrderCommand) -> OrderId:
        with self._uow:
            order = Order.create(cmd.customer_id, cmd.lines)   # 규칙은 도메인
            self._uow.orders.add(order)                        # 영속화는 Repository
            self._uow.commit()
        self._notifier.order_placed(order.id)                  # 알림은 Notifier
        return order.id

O — 개방-폐쇄 원칙 (Open/Closed)

확장에는 열려 있고 수정에는 닫혀 있어야 합니다. 분기(if type == ...)가 늘어난다면 전략(Strategy)으로 바꿉니다.

class DiscountPolicy(Protocol):
    def apply(self, order: Order) -> Money: ...

class VipDiscount:
    def apply(self, order: Order) -> Money:
        return order.total * Decimal("0.10")

class SeasonalDiscount:
    def apply(self, order: Order) -> Money:
        return order.total * Decimal("0.05")

class PricingService:
    def __init__(self, policies: Sequence[DiscountPolicy]) -> None:
        self._policies = policies

    def discount(self, order: Order) -> Money:      # 새 정책 추가 시 이 코드는 불변
        return max((p.apply(order) for p in self._policies), default=Money(Decimal(0)))

L — 리스코프 치환 원칙 (Liskov Substitution)

하위 타입은 상위 타입의 계약(사전조건 약화 불가, 사후조건 강화 불가, 예외 규약 유지)을 지켜야 합니다.

# ✗ 나쁨: 하위 클래스가 계약을 깨뜨림
class Repository(ABC):
    @abstractmethod
    def get(self, id: str) -> Customer: ...      # 없으면 CustomerNotFound

class CacheOnlyRepository(Repository):
    def get(self, id: str) -> Customer:
        raise NotImplementedError                # 치환 불가!

# ✓ 좋음: 모든 구현이 동일한 계약(없으면 CustomerNotFound)을 지키고,
#         계약 테스트(contract test)를 공유 fixture로 모든 구현에 실행
@pytest.fixture(params=[InMemoryRepo, SqlRepo])
def repo(request): ...

실무 팁: 하나의 추상 인터페이스에 대한 테스트 스위트를 작성해 모든 구현체가 통과하게 하면 LSP 위반을 자동으로 잡을 수 있습니다. mypy는 시그니처 호환성을 검사합니다.

I — 인터페이스 분리 원칙 (Interface Segregation)

클라이언트는 사용하지 않는 메서드에 의존하면 안 됩니다. 작은 역할(role) 인터페이스로 쪼갭니다. Python의 Protocol은 소비자 쪽에서 필요한 최소 계약만 선언하기 좋습니다.

# ✗ 나쁨: 뚱뚱한 인터페이스
class Storage(ABC):
    def read(self, key): ...
    def write(self, key, data): ...
    def delete(self, key): ...
    def list_all(self): ...

# ✓ 좋음: 역할별 분리
class Reader(Protocol):
    def read(self, key: str) -> bytes: ...

class Writer(Protocol):
    def write(self, key: str, data: bytes) -> None: ...

class ReportExporter:
    def __init__(self, writer: Writer) -> None:   # 쓰기만 필요
        self._writer = writer

D — 의존성 역전 원칙 (Dependency Inversion)

상위 모듈이 하위 모듈에 의존하지 않고, 둘 다 추상화에 의존합니다. 이 프로젝트에서는 application 계층이 외부 통신용 인터페이스(Port)를 소유하고, infra 계층이 그것을 구현합니다. 소스 코드 의존 방향이 infra → application이 되어 전통적인 "비즈니스 → DB" 방향이 뒤집힙니다.

# application/ports/repositories.py  (인터페이스는 application이 소유)
class CustomerRepository(Protocol):
    async def get(self, customer_id: CustomerId) -> Customer: ...
    async def add(self, customer: Customer) -> None: ...

# application/ports/payment_gateway.py
class PaymentGateway(Protocol):
    async def charge(self, order_id: OrderId, amount: Money) -> PaymentResult: ...

# application/order/place_order.py  (유스케이스는 Port만 안다)
class PlaceOrder:

8.2 Port 설계 규칙 (app 계층이 소유하는 인터페이스)

  • "외부와의 통신"은 전부 Port: DB(Repository/UoW), 메일·메신저(Notifier), 결제·CRM 등 외부 API(Gateway), 파일 저장소, 시계(Clock), ID 생성기 등. 유스케이스가 requests, smtplib, boto3를 직접 import하면 규칙 위반입니다.
  • 유스케이스 관점으로 정의: Port는 기술이 아니라 필요(send_order_confirmation(...))로 이름 짓습니다. SmtpClient가 아니라 Notifier입니다. (ISP: 역할별로 작게)
  • Port의 입출력은 도메인 객체·DTO·원시 타입: ORM 모델, HTTP 응답 객체, Pydantic 스키마가 Port 시그니처에 나타나면 안 됩니다.
  • Repository 위치에 대한 결정: 전통적 DDD는 Repository 인터페이스를 domain에 두기도 합니다. 이 프로젝트는 "외부 통신 인터페이스는 app이 소유"라는 일관된 규칙으로 application/ports에 모읍니다. 그 결과 domain은 영속성 개념을 전혀 모르는 완전히 순수한 모델로 남고, Repository는 Aggregate Root 단위로만 정의합니다.
  • Anti-Corruption Layer: 외부 시스템의 데이터 모델·오류 체계는 infra 어댑터 안에서 도메인 언어로 번역한 뒤 Port로 반환합니다. 외부 모델이 app/domain으로 새어 들어오지 않게 합니다.
  • 계약 테스트: Port마다 공통 테스트 스위트를 만들어 InMemory Fake와 실제 infra 구현을 모두 통과시킵니다(리스코프 치환 검증).

8.5 CQRS-lite

8.6 API 설계

14. 빌드와 패키징

산출물은 릴리스 번들(tar.gz) 하나입니다. 번들은 git SHA로 버전을 붙이고, 같은 번들을 dev에서 검증한 뒤 그대로 product에 배포합니다(빌드는 한 번).

14.1 릴리스 번들 구성

neoine-sales-<git-sha12>.tar.gz
└─ neoine-sales-<git-sha12>/
   ├─ VERSION                      # git SHA
   ├─ backend/
   │  ├─ pyproject.toml
   │  ├─ uv.lock                   # 서버에서 잠금 파일 기준으로 의존성 설치
   │  ├─ alembic.ini
   │  ├─ alembic/                  # 마이그레이션
   │  └─ src/app/                  # 애플리케이션 소스
   ├─ frontend/
   │  └─ dist/                     # pnpm build 결과(정적 파일)
   └─ infra/server/                # 서버 구성 자산: systemd 유닛, nginx 설정, sudoers, config.<profile>.json, bootstrap.sh
  • 가상환경(.venv)은 경로가 고정되어 옮길 수 없으므로 번들에 넣지 않고, 배포 서버에서 uv sync --locked --no-dev --no-editable로 릴리스 디렉터리 안에 생성합니다. --locked는 uv.lock이 최신인지 검증하고, --no-dev는 개발 의존성을 제외하며, --no-editable은 소스 의존 없이 패키지로 설치합니다(uv 공식 가이드의 옵션).
  • 서버는 인터넷의 PyPI에서 직접 의존성을 받습니다(uv.lock에 고정된 버전과 해시 기준). 따라서 서버에서 pypi.org, files.pythonhosted.org로의 outbound HTTPS가 필요합니다(16.6절 방화벽 허용 목록).
  • 서버의 Python은 bootstrap.sh가 uv python install로 .python-version(3.14)에 맞춰 neoine 계정에 설치합니다(GitHub의 python-build-standalone 다운로드). 이후 Python 버전을 올릴 때는 .python-version을 바꾼 릴리스를 배포하면 uv sync가 필요한 Python을 자동으로 받습니다.

14.2 번들 생성 스크립트

#!/usr/bin/env bash
# infra/build_release.sh <tag>  - Jenkins와 로컬에서 동일하게 사용
set -euo pipefail
TAG="${1:?usage: build_release.sh <tag>}"
NAME="neoine-sales-$TAG"
OUT="build/$NAME"

rm -rf build
mkdir -p "$OUT/backend" "$OUT/frontend"
cp -r backend/src backend/alembic backend/alembic.ini backend/pyproject.toml backend/uv.lock "$OUT/backend/"
cp -r frontend/dist "$OUT/frontend/dist"      # 사전에 pnpm build 실행
mkdir -p "$OUT/infra" && cp -r infra/server "$OUT/infra/server"
echo "$TAG" > "$OUT/VERSION"
tar -czf "build/$NAME.tar.gz" -C build "$NAME"
echo "created build/$NAME.tar.gz"

14.3 프론트엔드 빌드

  • pnpm install --frozen-lockfile && pnpm build → frontend/dist(정적 파일)를 번들에 포함하고, 서버의 Nginx가 직접 서빙합니다(16.5절).
  • 정적 파일은 해시된 파일명으로 장기 캐시, index.html은 no-cache로 서빙합니다.
  • 프로파일마다 다른 값은 빌드에 넣지 않고 서버가 제공하는 /config.json으로 주입합니다(3.5.8절).

15. CI/CD (Jenkins)

온프레미스 Linux 환경에서 Jenkins Declarative Pipeline(Jenkinsfile을 저장소에 포함, Pipeline as Code)으로 CI/CD를 구성합니다. Jenkins agent(Linux 빌드 노드)에서 직접 빌드·테스트하고, 릴리스 번들을 SSH로 서버에 전달해 배포합니다. 아래 문법(agent, options, when, input, withCredentials, post)은 Jenkins 공식 문서(Pipeline Syntax)를 확인해 작성했습니다.

15.3 브랜치·릴리스 전략

  • Trunk-based: main은 항상 배포 가능. 짧은 수명의 feature 브랜치 + PR(Merge Request).
  • PR 단계: Jenkins가 CI(검증)만 수행하고 결과를 Git 서버의 머지 조건(status check)으로 사용. 배포는 하지 않음.
  • main 머지: 릴리스 번들 생성·보관 → dev 프로파일 자동 배포(DB 마이그레이션 자동 적용) → 스모크/E2E → 수동 승인 → product(운영) 배포.
  • 번들 버전은 git SHA(불변). 릴리스는 Git 태그(SemVer)로 표시하고, 롤백은 서버에 남겨 둔 이전 릴리스로 전환(16.4절).
  • 커밋 규약은 Conventional Commits, 의존성 업데이트는 Renovate(사내 설치형)로 주기적 PR 생성.

15.5 Jenkinsfile 예시

최상위는 agent none으로 두고 단계마다 에이전트를 지정합니다(공식 문서의 stage-level agent 패턴). 빌드·테스트는 linux-build 노드에서, 배포는 deploy 노드에서 실행하며, 두 노드 간 산출물은 stash/unstash로 전달합니다.

// Jenkinsfile
pipeline {
    agent none

    options {
        timeout(time: 45, unit: 'MINUTES')
        timestamps()
        disableConcurrentBuilds()          // 같은 브랜치는 직렬 실행
        skipStagesAfterUnstable()
        buildDiscarder(logRotator(numToKeepStr: '30', artifactNumToKeepStr: '20'))   // 번들은 최근 20개 보관
    }

    environment {
        RELEASE_TAG = "${env.GIT_COMMIT.take(12)}"
        // 통합 테스트용 PostgreSQL 관리자 접속 정보 (agent 로컬 DB, 비밀 아님)
        TEST_DATABASE_ADMIN_URL = 'postgresql+asyncpg://ci@localhost:5432/postgres'
    }

    stages {
        stage('Backend: Quality') {
            agent { label 'linux-build' }
            steps {
                dir('backend') {
                    sh 'uv sync --locked'
                    sh 'uv run ruff check .'
                    sh 'uv run ruff format --check .'
                    sh 'uv run mypy src'
                    sh 'uv run lint-imports'
                    sh 'uv run python scripts/check_file_length.py'   // 파일 300줄 제한
                }
            }
        }

        stage('Backend: Test') {
            agent { label 'linux-build' }
            steps {
                dir('backend') {
                    sh 'uv sync --locked'
                    sh 'uv run pytest --junitxml=reports/junit.xml --cov-report=xml:reports/coverage.xml'
                }
            }
            post {
                always { junit 'backend/reports/junit.xml' }
            }
        }

        stage('Frontend: Quality & Test') {
            agent { label 'linux-build' }
            steps {
                dir('frontend') {
                    sh 'corepack enable && pnpm install --frozen-lockfile'
                    sh 'pnpm lint && pnpm typecheck'
                    sh 'pnpm test --run'
                    sh 'pnpm build'
                }
            }
        }

        stage('Contract & Security') {
            agent { label 'linux-build' }
            steps {
                dir('backend') {
                    sh '''
                        uv run python -c "import json; from app.main import app; print(json.dumps(app.openapi(), indent=2, sort_keys=True))" > /tmp/openapi.json
                        diff -u openapi.json /tmp/openapi.json
                    '''
                    sh 'uvx pip-audit'
                }
                sh 'trivy fs --scanners vuln --severity CRITICAL,HIGH --exit-code 1 backend/uv.lock frontend/pnpm-lock.yaml'
                sh 'gitleaks detect --no-banner --redact'
            }
        }

        stage('Package') {
            when { branch 'main' }
            agent { label 'linux-build' }
            steps {
                sh 'cd frontend && corepack enable && pnpm install --frozen-lockfile && pnpm build'
                sh 'infra/build_release.sh "$RELEASE_TAG"'
                archiveArtifacts artifacts: 'build/*.tar.gz', fingerprint: true   // 롤백·감사용 보관
                stash name: 'release', includes: 'build/*.tar.gz'
            }
        }

        stage('Deploy: Dev') {
            when { branch 'main' }
            agent { label 'deploy' }
            steps {
                unstash 'release'
                lock(resource: 'neoine-dev') {
                    withCredentials([sshUserPrivateKey(credentialsId: 'deploy-ssh-dev',
                                                       keyFileVariable: 'SSH_KEY',
                                                       usernameVariable: 'SSH_USER')]) {
                        sh '''
                            # 번들과 같은 커밋의 deploy.sh를 함께 전달 (스크립트도 코드와 함께 버전 관리)
                            scp -i "$SSH_KEY" -o StrictHostKeyChecking=yes \
                                "build/neoine-sales-$RELEASE_TAG.tar.gz" infra/server/deploy.sh \
                                "$SSH_USER@dev.internal.example.com:/opt/neoine-sales/incoming/"
                            ssh -i "$SSH_KEY" -o StrictHostKeyChecking=yes "$SSH_USER@dev.internal.example.com" \
                                "bash /opt/neoine-sales/incoming/deploy.sh dev $RELEASE_TAG"
                        '''
                    }
                }
                sh 'curl --fail --retry 5 --retry-delay 3 https://dev.internal.example.com/readyz'
            }
        }

        stage('Deploy: Product') {
            when {
                beforeInput true
                branch 'main'
            }
            input {
                message "product(운영)에 ${env.GIT_COMMIT.take(12)} 버전을 배포할까요?"
                ok '배포'
                submitter 'release-managers'      // 승인 가능한 사용자/그룹
            }
            agent { label 'deploy' }
            steps {
                unstash 'release'
                lock(resource: 'neoine-product') {
                    withCredentials([sshUserPrivateKey(credentialsId: 'deploy-ssh-product',
                                                       keyFileVariable: 'SSH_KEY',
                                                       usernameVariable: 'SSH_USER')]) {
                        // 서버를 한 대씩 순차 배포(롤링). 한 대라도 실패하면 중단
                        sh '''
                            for host in prd1.internal.example.com prd2.internal.example.com; do
                                scp -i "$SSH_KEY" -o StrictHostKeyChecking=yes \
                                    "build/neoine-sales-$RELEASE_TAG.tar.gz" infra/server/deploy.sh \
                                    "$SSH_USER@$host:/opt/neoine-sales/incoming/"
                                ssh -i "$SSH_KEY" -o StrictHostKeyChecking=yes "$SSH_USER@$host" \
                                    "bash /opt/neoine-sales/incoming/deploy.sh product $RELEASE_TAG"
                            done
                        '''
                    }
                }
            }
        }
    }

    post {
        failure { mail to: 'dev-team@example.com', subject: "FAILED: ${env.JOB_NAME} #${env.BUILD_NUMBER}", body: "${env.BUILD_URL}" }
    }
}

비밀 전달 규칙: withCredentials 안의 셸 명령은 작은따옴표(sh '...')로 작성해 셸이 변수를 확장하도록 합니다. 큰따옴표 Groovy 문자열에 비밀 변수를 넣으면 보간되어 로그·프로세스 목록에 노출될 수 있습니다. 또한 자격 증명은 해당 withCredentials 블록 안에서만 유효합니다.

product 배포 승인 단계는 input이 에이전트를 할당하기 전에 일시 정지되므로(공식 문서), 승인 대기 중에도 빌드 노드를 점유하지 않습니다. 단, 대기 시간이 길어질 수 있으니 options.timeout과 승인 단계의 타임아웃 정책을 함께 정하세요.

15.6 통합 테스트용 데이터베이스

통합 테스트는 실제 PostgreSQL 인스턴스에서 테스트 전용 데이터베이스를 만들어 실행합니다.

  • 로컬: 3.4절에서 설치한 PostgreSQL을 씁니다. 프로파일이 local이면 앱 설정의 접속 정보에서 DB 이름만 maintenance DB로 바꿔 임시 DB를 만들므로 별도 설정이 필요 없습니다(TEST_DATABASE_ADMIN_URL을 주면 그것을 우선합니다). 접속 role에 CREATEDB 권한이 필요합니다.
  • CI: linux-build agent에 PostgreSQL을 설치해 두고, CI 전용 role(ci, CREATEDB 권한만)로 접속합니다.
  • 격리: pytest 세션 fixture가 app_test_<무작위> DB를 CREATE DATABASE로 만들고 Alembic 마이그레이션을 적용한 뒤, 세션 종료 시 DROP DATABASE합니다. 이름이 매번 달라 같은 agent에서 병렬 빌드가 돌아도 충돌하지 않습니다. 운영 데이터가 있는 DB에는 절대 연결하지 않습니다.
  • 테스트 간 격리는 테스트마다 트랜잭션을 열고 롤백하는 방식(또는 테이블 TRUNCATE)을 사용합니다.

15.7 빌드 환경 (Agent)

  • 도구 버전 고정: 저장소 루트의 mise.toml에 Python, uv, Node, pnpm 버전을 적어 개발자 PC(맥/Windows WSL2)와 CI agent가 같은 버전을 쓰게 합니다. agent는 최초 1회 mise를 설치하고 빌드 시작 시 mise install을 실행합니다. Trivy, gitleaks, PostgreSQL은 OS 패키지나 공식 릴리스로 설치하고 설치 버전을 운영 문서에 기록합니다.
  • 인터넷 직접 연결: agent는 PyPI(pypi.org, files.pythonhosted.org), npm(registry.npmjs.org), GitHub(github.com, objects.githubusercontent.com: uv의 Python 다운로드, mise, Trivy/gitleaks 릴리스)로 outbound HTTPS가 가능해야 합니다. 사내 프록시가 있으면 HTTPS_PROXY/NO_PROXY를 agent 환경에 설정합니다.
  • 공급망 보호: 인터넷에서 직접 받는 만큼 uv sync --locked, pnpm install --frozen-lockfile로 잠금 파일에 고정된 버전만 설치하고, pip-audit, pnpm audit, Trivy로 취약점을 매 빌드 점검하며, Renovate로 의존성 갱신을 PR로 검토합니다.
  • workspace는 빌드 후 정리(Workspace Cleanup)하고, agent 디스크의 uv 캐시는 주기적으로 정리합니다.

16. 온프레미스 Linux 운영 환경

systemd + Nginx + 릴리스 디렉터리로 운영합니다. 애플리케이션은 전용 계정(neoine)의 systemd 서비스로 실행하고, 배포는 릴리스 디렉터리를 새로 만든 뒤 current 심볼릭 링크를 바꾸는 방식입니다.

16.3 FastAPI 실행 방식

  • systemd가 Uvicorn의 --workers N(또는 fastapi run --workers N)로 다중 프로세스를 실행합니다. 프로세스 감시·재시작은 systemd(Restart=on-failure)가 담당합니다.
  • Uvicorn은 127.0.0.1:8000에서만 대기하고 외부 접근은 Nginx를 거칩니다. Nginx 뒤에서는 --proxy-headers를 지정해 실제 클라이언트 IP/스킴을 인식합니다. 같은 서버의 Nginx만 접근하므로 신뢰 프록시는 로컬호스트로 충분합니다. 다른 호스트의 프록시를 신뢰해야 할 때만 --forwarded-allow-ips를 지정하세요.
  • 경로 접두어를 프록시에서 제거한다면 --root-path를 지정합니다(문서/OpenAPI URL 정합성).
  • 워커 수는 --workers(유닛 파일)와 설정값 APP_WORKERS가 같도록 관리합니다. --workers는 유닛 파일(infra/server/systemd/)에서 고치고, 설정값은 서버 .env에서 고쳐 두 곳을 함께 변경합니다.

#!/usr/bin/env bash
# infra/server/deploy.sh <dev|product> <release_tag>   (Jenkins가 서버로 전달해 실행. 계정: neoine)
set -euo pipefail
ENV_NAME="$1"; TAG="$2"
case "$ENV_NAME" in dev|product) ;; *) echo "알 수 없는 프로파일: $ENV_NAME" >&2; exit 2 ;; esac

APP_HOME=/opt/neoine-sales
RELEASE="$APP_HOME/releases/$TAG"
cd "$APP_HOME"
export PATH="$HOME/.local/bin:$PATH"   # uv 위치 (비대화형 SSH 세션용)

# .env의 APP_PROFILE이 대상 환경과 같은지 확인 (dev 설정이 product 서버에 올라가는 사고 방지)
grep -qx "APP_PROFILE=$ENV_NAME" .env || { echo "APP_PROFILE이 $ENV_NAME 과 다릅니다" >&2; exit 2; }

PREV="$(readlink -f current 2>/dev/null || true)"

# 1) 번들 풀기 + 의존성 설치 (잠금 파일 기준, 개발 의존성 제외. PyPI에서 직접 다운로드)
mkdir -p "$RELEASE"
tar -xzf "incoming/neoine-sales-$TAG.tar.gz" -C "$RELEASE" --strip-components=1
( cd "$RELEASE/backend" && uv sync --locked --no-dev --no-editable )

# 1-1) 설정 사전 검증: 필수 변수 누락·형식 오류·product 안전 조건 위반이면 여기서 중단 (전환 전)
( cd "$APP_HOME" && "$RELEASE/backend/.venv/bin/python" -c "from app.config import get_settings; get_settings()" )

# 1-2) 프론트 런타임 설정 설치 (비밀 없음)
install -m 644 "$RELEASE/infra/server/config/config.$ENV_NAME.json" shared/config.json

# 2) DB 마이그레이션 (하위 호환 변경만: expand -> migrate -> contract)
#    cwd=$APP_HOME 이어야 .env를 읽는다. 마이그레이션 실패 시 set -e로 여기서 중단(전환 전)
"$RELEASE/backend/.venv/bin/alembic" -c "$RELEASE/backend/alembic.ini" upgrade head

# 3) 전환 + 재시작 (심볼릭 링크 교체는 원자적)
ln -sfn "$RELEASE" current.new && mv -T current.new current
sudo systemctl restart neoine-sales-api

# 4) 헬스체크, 실패 시 롤백
for i in $(seq 1 30); do
  if curl -fsS --max-time 3 http://127.0.0.1:8000/readyz >/dev/null; then
    echo "배포 성공: $TAG"
    # 5) 오래된 릴리스 정리 (최근 5개 + 현재 보관)
    ls -1dt releases/*/ | tail -n +6 | xargs -r rm -rf
    find incoming -name 'neoine-sales-*.tar.gz' -mtime +14 -delete
    exit 0
  fi
  sleep 3
done

echo "헬스체크 실패 - 롤백: $PREV" >&2
if [ -n "$PREV" ]; then
  ln -sfn "$PREV" current.new && mv -T current.new current
  sudo systemctl restart neoine-sales-api
fi
exit 1

롤백은 코드만 이전 릴리스로 되돌리는 것이므로, 마이그레이션이 하위 호환(expand/contract)이어야 안전합니다. 파괴적 스키마 변경은 앱 배포와 분리해 단계적으로 진행하세요. 마이그레이션 정책: local과 dev는 자동 적용(dev는 deploy.sh dev가 alembic upgrade head를 실행하고, 실패하면 전환 전에 배포를 중단)이고, product만 dev 검증 후 Jenkins 승인(input)을 거쳐 같은 deploy.sh가 실행합니다. dev에 자동 적용되므로 모든 마이그레이션은 하위 호환이어야 합니다. product는 서버를 한 대씩 순차 배포(Jenkinsfile의 롤링 루프)하며, 로드밸런서 헬스체크가 재시작 중인 서버로 요청을 보내지 않도록 구성합니다. 배포 계정(neoine)에는 neoine-sales-api의 systemctl restart만 허용하는 sudoers 규칙을 부여합니다(infra/server/sudoers/neoine-sales, bootstrap.sh가 설치).

    }
}

TLS 인증서는 사내 CA 또는 사내 ACME(step-ca 등)로 발급하고 만료 알림/자동 갱신을 구성합니다. 프론트 정적 파일은 current 링크를 통해 서빙되므로 배포 시 Nginx 재시작이 필요 없습니다.

16.6 서버 최초 구성 (수동 부트스트랩)

서버 구성 자산은 저장소의 infra/server/에 두고, 서버당 최초 1회 관리자가 bootstrap.sh를 실행합니다. 스크립트는 멱등(여러 번 실행해도 같은 결과)이며, 설정 파일(systemd·Nginx·sudoers)을 바꿀 때도 같은 스크립트를 다시 실행합니다. 서버가 여러 대면 서버마다 실행합니다.

infra/server/
├─ bootstrap.sh                    # 최초 구성·설정 재적용 (root/sudo)
├─ deploy.sh                       # 배포/롤백 (16.4절, Jenkins가 매 배포 시 전달)
├─ systemd/ (neoine-sales-api.service)
├─ nginx/neoine-sales.conf         # 16.5절
├─ sudoers/neoine-sales            # neoine 계정의 systemctl restart 허용 범위
└─ config/ (config.dev.json, config.product.json)   # 프론트 런타임 설정, 비밀 없음
#!/usr/bin/env bash
# infra/server/bootstrap.sh <dev|product>   - 서버당 최초 1회, root(sudo)로 실행. 멱등.
set -euo pipefail
ENV_NAME="${1:?usage: bootstrap.sh <dev|product>}"
UV_VERSION="0.10.4"          # uv.lock을 만든 uv와 같은 버전으로 고정
PYTHON_VERSION="3.14"        # backend/.python-version 과 일치
HERE="$(cd "$(dirname "$0")" && pwd)"
APP_HOME=/opt/neoine-sales

# 0) 사전 설치(OS 패키지, 배포판에 맞게 수동): nginx, curl, tar, (DB 서버는 별도 호스트)
#    예) Ubuntu: apt install nginx curl    /  Rocky: dnf install nginx curl

# 1) 서비스/배포 계정 (SSH 키 인증 전용. 키는 Jenkins 배포 키의 공개키를 등록)
id neoine &>/dev/null || useradd --create-home --shell /bin/bash neoine
install -d -o neoine -g neoine -m 750 "$APP_HOME" "$APP_HOME/incoming" "$APP_HOME/releases" "$APP_HOME/shared"

# 2) uv와 Python (neoine 계정, 인터넷에서 직접 다운로드)
sudo -u neoine -H sh -c "curl -LsSf https://astral.sh/uv/$UV_VERSION/install.sh | sh"
sudo -u neoine -H "/home/neoine/.local/bin/uv" python install "$PYTHON_VERSION"

# 3) 설정 파일 설치 (systemd, nginx, sudoers) - 배포판별 nginx 경로(conf.d / sites-enabled)에 맞게 조정
install -m 644 "$HERE"/systemd/*.service /etc/systemd/system/
install -m 644 "$HERE/nginx/neoine-sales.conf" /etc/nginx/conf.d/neoine-sales.conf
install -m 440 "$HERE/sudoers/neoine-sales" /etc/sudoers.d/neoine-sales
visudo -cf /etc/sudoers.d/neoine-sales
systemctl daemon-reload
systemctl enable neoine-sales-api     # 시작은 첫 배포 때
nginx -t && systemctl reload nginx

# 4) .env 생성: APP_PROFILE만 채우고 나머지 비밀은 관리자가 직접 입력 (이미 있으면 보존)
if [ ! -f "$APP_HOME/.env" ]; then
  install -m 600 -o neoine -g neoine /dev/null "$APP_HOME/.env"
  echo "APP_PROFILE=$ENV_NAME" > "$APP_HOME/.env"
  echo "필수 변수(3.5.3절)를 neoine 계정으로 $APP_HOME/.env 에 입력하세요."
fi
# infra/server/sudoers/neoine-sales  (명령 경로는 배포판에 맞게: which systemctl)
neoine ALL=(root) NOPASSWD: /usr/bin/systemctl restart neoine-sales-api

  • ☐ OS 패키지 설치(nginx 등), 시간 동기화(chrony), 패치 정책 수립(월간)과 재부팅 윈도우 정의
  • ☐ bootstrap.sh <dev|product> 실행, Jenkins 배포 공개키를 neoine 계정 ~/.ssh/authorized_keys에 등록
  • ☐ TLS 인증서 배치(사내 CA 등), /opt/neoine-sales/.env에 필수 변수 입력(권한 600, 소유자 neoine)
  • ☐ DB(PostgreSQL)에 애플리케이션용 최소 권한 계정 생성, 마이그레이션 계정과 분리 여부 결정
  • ☐ SSH 하드닝: 비밀번호 로그인 차단, root 직접 로그인 차단, 키 인증만 허용

보안

관측성

  • 로그: structlog JSON 로그 + 요청별 상관관계 ID.
  • 메트릭/트레이스: OpenTelemetry → Prometheus/Grafana(자세한 셀프 호스팅 스택은 16.7 참고).
  • 오류 추적: Sentry 셀프 호스팅 또는 GlitchTip(백엔드·프론트 모두).
  • 헬스체크: /healthz(liveness), /readyz(DB 연결 포함 readiness).

운영

  • DB 백업/복구 리허설, 마이그레이션 롤백 절차 문서화.
  • SLO(가용성·지연) 정의와 알림 설정, 장애 회고(blameless postmortem).
  • Feature Flag(예: Unleash, 자체 구현)로 위험한 변경을 점진 배포.
